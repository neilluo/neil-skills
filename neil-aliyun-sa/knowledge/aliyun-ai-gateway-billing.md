`[推断]` **两条派生规律（官方未明写，仅供 SA 快速估算与自检，不得对客作为报价依据）**：

1. **包年包月 ≈ 按量付费满月价的 7 折**。对全部 45 行计算 `包月单价 ÷ (按量单价 × 720 小时)`，结果落在 **0.6997 ～ 0.7001** 区间（例：`aigw.medium.x1` 中国内地 56.1 × 720 × 0.7 = 28,274.4，表中为 28,276）。→ 官方页面**未出现「折扣」「7 折」字样**，此为反推。
2. **地域倍率对 9 个规格恒定**：以中国内地为 1.0，金融云 = **1.9×**、中国香港/日本（东京）= **1.5×**、新加坡/雅加达/法兰克福 = **1.38×**、美国（弗吉尼亚/硅谷）= **1.2×**（每档 9 个规格算出的倍率一致，误差 < 0.001）。→ 可用于「客户报了一个海外地域，只知道内地价」时的**量级**估算，但仍属外推，成交前必须走价格页。

#### 3.2.4 数据处理量费用（🔴 私网比公网贵）

官方口径：「创建 AI 网关专享实例时，可选择的网络类型包括公网、私网、公网+私网。**不同网络类型的数据处理量单独计费**。在一个计费周期内，数据处理量为**请求和响应的数据量之和**。」

| 地域档位 | 网络类型 | 单价（元/GB/小时） | 相对同档公网 |
|---|---|---|---|
| 公共云 | 公网 | 0.037 | 基准 |
| 公共云 | 私网 | 0.049 | `[推断]` 1.3243× （0.049 ÷ 0.037） |
| 金融云 | 公网 | 0.07 | `[推断]` 1.8919× 于公共云公网 |
| 金融云 | 私网 | 0.093 | `[推断]` 1.898× 于公共云私网 |

来源：`free-product-templates`。

🔴 **SA 反直觉点**：专享实例**私网数据处理量单价（0.049）高于公网（0.037）**。客户常说「我全走内网更便宜」——在专享实例的数据处理量这一项上**不成立**。

官方计费公式与示例（逐字）：

> 公网：单位小时费用 = 数据处理量 × 单价。
> 例如：使用网关实例 2 小时，第一个小时产生了 5 GB 数据量，第二个小时产生了 10 GB 数据量，那么 2 小时的数据处理量总费用为 0.037×5 + 0.037×10 = 0.555 元。
> 私网：单位小时费用 = 数据处理量 × 单价。
> 例如：……0.049×5 + 0.049×10 = 0.735 元。

🔴 **本表地域粒度与 3.2.3 实例费用表不一致（同页内部口径差）**：实例费用按 **5 个地域档**定价（内地／金融云／港+东京／新+雅+法／美国），而数据处理量只按 **2 个档**（公共云／金融云）。即：官方此表把中国内地、港/东京、新/雅/法、美国**全部归入「公共云」一档 0.037／0.049**，海外地域的数据处理量**未单列单价**。`[文档未说明]` 是否确实所有公共云地域同价，还是官方漏列海外档 —— 对客报价前必须核验。

### 3.3 Serverless 新版（标准版／企业版）计费

> 页面 slug 为 `overview-of-billing-during-the-serverless-public-preview-of-the`（含 "public-preview"），TSV 官方链接文字为「AI网关Serverless新版**公测**计费说明」，**但正文写的是商业化后口径**。见 §3 溯源的 `[官方矛盾]` 条目 M1。

#### 3.3.1 适用范围（原文逐字，含排除项）

> 本文适用于 AI 网关 Serverless 新版（Serverless 标准版和 Serverless 企业版）**商业化后**的计费说明，**不适用于 Serverless（旧）实例和实例型独享版**。
> 模型服务、日志服务、云监控等其他云产品的费用，由对应云产品单独计费。

> 具体可购买的实例类型、价格、折扣、出账周期和可用地域，请以**产品控制台**、官网价格页和**费用与成本**页面展示为准。

#### 3.3.2 标准版 vs 企业版 计费与能力差异（7 行全量）

| 对比项 | Serverless 标准版 | Serverless 企业版 |
|---|---|---|
| 起步成本 | 0 元起步，无实例费 | 有实例费 |
| 计费方式 | 按实际用量计费 | 实例费 + 按实际用量计费 |
| 入口能力 | 使用平台分配入口 | 提供独立入口能力 |
| 自定义域名和传输加密配置 | **不支持**用户自定义配置 | 支持自定义域名、证书、TLS policy 和 HTTP/2 配置 |
| 公网流量 | 出网、入网均由网关侧计费，0.8 元/GB | 出网、入网均由网关侧计费，0.8 元/GB |

| 请求特征 | 计量请求次数 |

#### 3.4.4 各 API 类型的 CU 系数（🔴 Model API 是 Agent API 的 5 倍）

官方公式（逐字）：

```plaintext
单个 API CU = CU 系数 × 向上取整{（该 API 请求 payload + 该 API 响应 payload）/ 512 KB}
```

| API 类型 | CU 系数 |
|---|---|
| Model API | 10 |
| MCP Server | 5 |
| Agent API | 2 |

来源：`serverless-old-billing-details`。

官方示例（逐字）：

> * 某 Model API 请求，请求 payload 为 100 KB，响应为 800 KB，则该次请求的 CU 为 10 × 向上取整{(100+800)/512} = 20。
> * 某 MCP Server 请求，请求 payload 为 50 KB，响应为 300 KB，则该次请求的 CU 为 5 × 向上取整{(50+300)/512} = 5。

`[推断]` 由公式 + 系数可得两条对客要点：(1) payload 以 **512 KB 为一个计费台阶**且向上取整，**不足 512 KB 也按 1 个台阶算**，因此小请求的 CU 单价被系数完全决定；(2) 同样一次调用，走 Model API 的 CU 成本是走 Agent API 的 **5 倍**（10 ÷ 2）、是 MCP Server 的 **2 倍**（10 ÷ 5）。旧版存量客户做「Model API → Agent API」形态改造有直接账单收益（但需评估能力差异，能力对比不在本页）。

#### 3.5.4 🔴 无法估算的空白：AI 增强能力的 Credits 折算率（2026-09-21 主控收窄口径）

> ⚠️ **本条原标题把折算率的缺失范围写成了「全库」，经独立评审 R1 回源判定为 D3「空白被填」过宽，主控已收窄。**
> **模型调用侧的 Credits 机制是有文档的**：`model-metadata` 明文——模型元信息可配「输入 / 输出 / 缓存 Credits 单价」，
> 「单位 **Credits/1M tokens**，如填写必须为大于等于 0 的数字，最多两位小数，**默认值为 0**」`[官方原文｜model-metadata]`
> （详见 [§4 对象模型](aliyun-ai-gateway-traffic.md) 的模型元信息节）。
> 即：**模型调用的 Credits 消耗原则上可算** = Token 用量 × 该模型配置的 Credits/1M tokens 单价 ÷ 1M；
> 🔴 但**默认值为 0**，客户不主动填就是 0，且官方未说明填 0 时是否等于不计费还是走别的口径。

**真正的空白在 AI 增强能力侧**：官方说「按实际使用量折算为 Credits 消耗」、「Credits 消耗量与实际使用的 AI 增强能力类型和用量相关」，但 `ai-credits-billing-details` **全页没有给出任何折算率**——一次智能路由决策消耗多少 Credit、按请求次数还是按 Token 还是按候选模型数折算，`[文档未说明]`；语义检索、工具精选是否消耗 Credits 亦 `[文档未说明]`（见 [§8](aliyun-ai-gateway-mcp-agent.md)）。
→ **后果**：SA **无法给出智能路由/语义检索/工具精选的成本量级**，只能给单价 0.01 元/Credit。报价前必须找产品侧确认或让客户在控制台试跑看账单。

#### 3.6.2 三条必须写进对客材料的地域纪律

### 3.9.2 服务可用性：计算口径与承诺值

**计算方式（原文逐字）**：

> 网关的服务可用性**以单个实例为维度**，通过计算服务周期内**每5分钟错误率的平均值**，从而计算得出服务可用性，即：
> 服务可用性=（1-服务周期内Σ每5分钟错误率/服务周期内5分钟总个数）x100%
> （注：服务周期内5分钟总个数=**12 x 24 x 该服务周期的天数**）

🔴 **SA 必须讲清的口径陷阱（`[推断]`，基于官方公式）**：可用性 = **1 − 各 5 分钟错误率的算术平均**，**不是** 1 − (全月失败总数 ÷ 全月请求总数)。
后果：**低流量的 5 分钟窗口与高流量窗口等权**。一个夜间只有 10 个请求、失败 1 个的窗口，其错误率 10% 与一个白天百万请求失败 1% 的窗口在公式里**权重相同**。

**月度「错误预算」量级（`[推断]`，把官方公式反解成 SA 能对客说的分钟数）**：
取 30 天自然月，服务周期内 5 分钟总个数 = 12 × 24 × 30 = **8640**（官方注：12 × 24 × 该服务周期的天数）。
令 Σ每5分钟错误率 = S，则可用性 = (1 − S ÷ 8640) × 100%。反解「刚好达标」的 S 上限：

| 实例类型 | 承诺 | S 上限（每5分钟错误率以小数计） | 折算成「整窗口 100% 失败」的窗口数 | 折算成全月完全不可用时长 |
|---|---|---|---|---|
| 普通实例 | 99.99% | S ≤ (1 − 0.9999) × 8640 = **0.864** | **0.864 个** | **≈ 4.32 分钟/月** |
| serverless实例 | 99.90% | S ≤ (1 − 0.9990) × 8640 = **8.64** | **8.64 个** | **≈ 43.2 分钟/月** |

来源：承诺值取自 `sla-agreement-fulltext-terms-alicdn` §2.2；S 上限、窗口数、分钟数三列全部为 `[推断]`（由官方公式 §2.1 + 注「12 x 24 x 该服务周期的天数」反解）。

（换算：1 个「整窗口 100% 失败」贡献 S = 1.0；窗口长 5 分钟，故 0.864 × 5 = 4.32 分钟、8.64 × 5 = 43.2 分钟。2 月按 28 天算则总数为 8064，上限分别为 0.8064 / 8.064。）
⚠️ 上表为**推导值**，SLA 原文只给公式、不给分钟数，且**未说明**按 30 天还是按当月实际天数示例。

`[推断]` **对客两句话结论**：
1. **普通实例 99.99% ≈ 一个月只允许约 4.3 分钟的全窗口不可用**，Serverless 99.90% ≈ 约 43 分钟 —— 这是「承诺线」，不是「赔偿线」以外还有余量。
2. 因为分母是「5 分钟窗口个数的算术平均」，**低峰期的小流量故障对可用性的拉低作用被放大**：夜间一个只有 10 个请求、失败 5 个的窗口贡献 S = 0.5，已经吃掉普通实例月度预算（0.864）的 **58%**。→ 客户「感觉没挂多久就跌破 99.99%」通常是这个原因，不是官方算错。
