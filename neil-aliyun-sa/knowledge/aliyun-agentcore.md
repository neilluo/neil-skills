## 2. 核心概念与资源对象模型

### 2.1 资源边界：一切以 Workspace 为界

官方定义（逐字）：「AgentCore 中的资源以 Workspace 为边界组织。Workspace 内独立维护模型配置、Agent、Team 和 MCP 工具。Agent 是执行 AI 任务的单元，运行时关联一个模型，并可绑定 Skill 与 MCP；多个 Agent 可组成 Team。」（`agentcore-basic-concepts`）[官方]

- **Workspace = 资源隔离和管理的基本单元**；「模型连接、Agent、Team、Skill、MCP 工具和凭证等资源均归属于某个 Workspace」（`manage-workspace`）[官方]
- **开通 AgentCore 服务时需创建一个 Workspace**，开通完成后即可直接使用；后续可根据需要创建更多（`manage-workspace`）[官方]
- 🔴 **Agent 运行时关联「一个」模型（单数）**，官方原文未提供多模型并行（`agentcore-basic-concepts`）[官方]
- **对客含义**：多业务线/多环境隔离要靠多 Workspace，而不是靠命名规范；且 Workspace 是**跨地域的** —— 「记忆空间归属于指定地域的 Workspace。查看数据前，请确认所选地域和 Workspace 与创建时一致」（`manage-memory-space`）[官方]

**创建 Workspace 的配置项只有 3 个**（`manage-workspace` 表，原样搬运）[官方]：

| 参数 | 说明 |
|---|---|
| 绑定 VPC | 是否为 Workspace 配置私有网络资源。**关闭时不展示以下参数**；打开后需完成 VPC 与交换机配置 |
| VPC | **必填**。选择 Workspace 使用的专有网络 |
| 交换机 | **必填**。选择 VPC 后可选 |

🔴 **绑 VPC 的硬约束（逐字，`manage-workspace` 与 `view-overview` 双页同文）**：「需选择至少 2 个交换机，并确保覆盖至少 2 个不同可用区。」[官方]
→ **对客含义**：客户若只有单可用区 VPC，开 Workspace 绑网就会卡住。这是**方案评审前必须先查的客户侧前置条件**，不是 AgentCore 侧可放宽的参数。[推断] 依据：①「交换机 必填。选择 VPC 后可选」②「需选择至少 2 个交换机，并确保覆盖至少 2 个不同可用区」——两条均为逐字原文，组合即得「单可用区 VPC 无法满足该必填校验」。

- 另有：**创建 Workspace 时会自动绑定 AgentLoop**，可以查看 AgentLoop 的相关信息（`view-overview`）[官方]
  ⚠️ 该页**未提及 AgentLoop 是什么、其配额或计费** → 缺口，且 AgentLoop 属主控 RULINGS R3 裁定**不在本次蒸馏范围**的相邻产品，对客不得展开。

#### 2.2.1 连接器（Connector）—— 目前只有一种

- 🔴 **「当前支持集成 Qoder CLI，即托管 Qoder 类型的 Agent。」（逐字，页面只列出这一种连接器）**（`manage-connectors`）[官方]
- 启用 Qoder CLI 需配置（原样搬运）[官方]：

| 参数 | 说明 |
|---|---|
| **站点** | 被集成 Qoder 账号所属的站点，支持**中国站**和**国际站** |
| **组织 ID** | 要集成的 Qoder 组织 ID |
| **API 密钥** | Qoder 控制台的 API 密钥，**用于换取 Qoder 访问凭证（SAT）**。**配置后加密存储于工作空间 Vault** |
| **服务账号** | AgentCore 访问 Qoder 所使用的服务账号，包括账号名称和凭证。单击**新增服务账号**可以添加多个 |

- 鉴权链路：填 API 密钥 → 换取 Qoder 访问凭证（SAT）→ 密钥加密存储于**工作空间 Vault**；提供**连通性校验**按钮；连接器状态只有**未启用**/**已启用**两种 [官方]
- 缺口：未提及连接器数量上限、服务账号数量上限、SAT 有效期与轮换机制、除 Qoder CLI 外的连接器路线图 [官方未提及]

#### 2.2.2 记忆空间 —— 长期记忆 vs 会话历史（原样搬运）[官方]

| 对比项 | 长期记忆 | 会话历史 |
|---|---|---|
| 保存的内容 | 从输入中提取的偏好、事实和需求等信息 | 会话中的消息记录 |
| 主要用途 | 在后续交互中检索和复用信息 | 查看和追溯交互过程 |
| 查看方式 | 查看记忆列表、详情，或进行语义检索 | 查看会话列表，再查看指定会话的消息 |
| 示例 | 用户偏好素食餐厅 | 用户表达该偏好时的消息，以及助手的回复 |

🔴 **三条会被客户误解的限制（逐字）**[官方]：
1. 「创建记忆空间后，还需要通过支持的接入方式写入数据。**创建空间本身不会自动收集所有 Agent 的对话**；会话历史中展示的内容取决于应用实际提交的消息。」
2. 「**输入内容与生成的记忆不一定一一对应。**提交一段文本或一组消息后，可能生成多条记忆，也可能不生成新记忆。」
3. 「**语义检索**受查询文本、Scope、Metadata、返回数量和检索阈值影响，**不保证返回全部符合筛选条件的记忆**。」

- **Scope**（`userId` / `agentId` / `sessionId`）**均由应用自行定义和传入**；查询时「指定的字段参与精确过滤，未指定的字段不参与过滤；多个字段同时指定时，需要同时满足这些条件」[官方]
- 🔴 「**`userId` 是业务字段，不对应 RAM 用户或调用身份**；应用需要自行维护这些业务标识，并在写入和查询时一致使用。」[官方] → 对客做数据隔离方案时，**不能拿 RAM 体系当记忆隔离边界**。
- **Metadata** = 字符串键值对的自定义业务标记；「Scope 表达记忆的业务归属，Metadata 表达记忆的业务属性」[官方]
- 空间状态需变为 `Ready` 后才能读写；**删除记忆空间会删除空间内数据，重新创建同名空间不能恢复；删除是异步操作**[官方]
- OpenAPI 保留 `MemoryStore` 作为记忆空间的资源标识名称；API 清单：`CreateMemoryStore`/`GetMemoryStore`/`ListMemoryStores`/`UpdateMemoryStore`/`DeleteMemoryStore`、`AddMemories`、`SearchMemories`、`ListMemories`/`GetMemory`/`UpdateMemory`/`DeleteMemory`、`ListMemorySessions`/`ListMemorySessionMessages`（属 §6，此处仅登记存在性）[官方]

#### 2.2.3 模型管理 —— 只支持手动填 API Key

- 「模型管理功能支持接入多个 AI 模型供应商，统一管理 API 端点和认证信息，并在正式使用前验证模型可用性」[官方]

#### 2.2.5 MCP Server —— 无内置目录，全部自建接入

|---|---|

#### 2.2.6 凭证 —— key-value 环境变量，仅此一种形态

- 🔴 **「目前支持的凭证类型为 key-value 形式，以环境变量形式提供。」（逐字）**[官方] → 即**不支持文件型/证书型凭证**（此结论由该逐字句的排他性得出，官方未正面列举不支持项）
- Key = 凭证的**环境变量名**（例如 `OPENAI_API_KEY`；`agentcore-basic-concepts` 举例 `GITHUB_ACCESS_TOKEN`），**Value 创建后默认隐藏**[官方]
- 官方安全风险原文：「API Key 等凭证等同于访问外部服务的身份密钥。一旦泄露，他人即可冒用该凭证调用对应服务，可能造成资费损失、配额被占用、数据泄露或服务被滥用等风险。」[官方]
- 官方建议三条（逐字）：不在代码仓库、日志、截图、聊天或工单等场景中以明文形式暴露凭证 ｜ 遵循最小权限原则，为不同用途或环境使用相互独立的凭证 ｜ 定期轮换凭证；一旦怀疑泄露，立即在对应供应商侧吊销原凭证并更换新凭证 [官方]
- 🔴 **加密存储口径不一致**：`manage-connectors` 写 Qoder API 密钥「配置后加密存储于**工作空间 Vault**」，而 `manage-credentials` **全页未出现 Vault 字样、未提及凭证的加密存储机制** [官方矛盾]（照实并列，不替官方调和）→ 对客谈「凭证加密落盘」时，**只有连接器侧有原文，凭证管理侧无原文**，不得外推。

**工作目录**：启动命令含 `--work-dir` 时用该参数指定目录；**未指定时使用执行连接命令时所在的当前目录**；建议用绝对路径；「目录应仅授予完成任务所需的权限」；🔴「**工作目录应遵循最小权限原则，不应直接设置为用户主目录或包含无关敏感文件的上级目录**」[官方]

**🔴 交付语义（客户最容易踩）**：「**Agent 在本地生成的文件不会自动上传到 Team。需要交付文件时，任务描述应明确要求以附件形式提交；如果回复中仅包含本地路径，文件仍保存在运行机器上。**」[官方]

**会话控制命令**：`/stop` = 终止当前执行，**不清空上下文** ｜ `/clear` = 终止当前执行并清空会话上下文，**清空上下文**；「通过 Team 群聊或任务会话发送控制命令时**同时 @ 目标 Agent**」；「**控制命令单独发送，不与普通任务内容合并**」[官方]

**🔴 凭据安全（逐字告警）**：「启动命令包含连接凭据和云监控配置，属于敏感信息。**不得将完整启动命令、bootstrap token 或云监控配置保存到代码仓库、文档、工单、日志系统或即时通信记录中。**」；「**每次生成的令牌明文仅在当前页面展示，关闭页面后无法再次查看，需要重新签发。**」；「启动命令疑似泄露时，**立即重新生成，旧命令停止使用**」；「**日志和排障反馈中不得包含 token 或完整启动命令。**」[官方]

**启动命令两步不可拆**：「1. 安装并配置 LoongSuite Pilot；2. 连接并纳管 Agent。」🔴「单击**复制全部**按顺序执行全部命令，**不得跳过第 1 步，也不得仅复制第 2 步**」；「以页面生成的命令为准，**不手工修改连接凭据和云监控参数**」[官方]

**本地实例状态 8 态（原样搬运）**[官方]：`pending`=实例正在准备 ｜ `running`=正常运行 ｜ `waiting`=等待运行时满足启动条件 ｜ `degraded`=已运行但连接、心跳或部分能力异常 ｜ `failed`=启动失败 ｜ `stopping`=已请求断开，进程正在停止 ｜ `disabled`=实例已断开（需恢复时重新连接）｜ `stale`=记录的进程已不再活动

**运维命令与安全红线**[官方]：
- `worker disconnect INSTANCE_ID`（断开，**实例停止运行，本机实例配置保留**）｜ `worker connect INSTANCE_ID`（重连）｜ `worker delete INSTANCE_ID`（删除）｜ Pilot 级 `status`/`info`/`start`/`restart`/`worker list`/`worker status`
- 🔴「**删除前需等待实例停止**」；「**删除本地实例不会删除控制台中的纳管 Agent。不再使用时，还需在控制台删除对应 Agent。**」
- 🔴「**重启 Pilot 会影响该机器上的全部本地纳管实例**」（服务状态异常时，确认没有正在执行的重要任务后再 `restart`）
- 🔴「**同一纳管 Agent 不应同时启动多个本地副本**」；「**迁移机器前必须先断开旧机器实例**」
- 缺口：未提及单台运行机器可纳管的实例数量上限、单个 Team 可加入的纳管 Agent 数量上限、**支持地域清单**、**本页能力处于公测还是商用**、是否需白名单或申请开通、bootstrap token 有效期时长、云监控 2.0 工作空间的开通前提与费用、本地纳管 Agent 的计费方式 [官方未提及]

**两条 `[推断]` 判据（附推理依据原文）**：

1. `[推断]` **高代码路径的隐性成本 = 客户自己写接入代码**；托管 Harness 路径则由平台代生成。
   依据：①「使用平台模型、MCP 或 Skill 时，**由代码引用相应资源**。**高代码创建页不会像托管 Harness 一样替应用生成提示词、选择模型或注册工具**，具体接入方法请参见对应语言的 SDK 使用指南」②托管 Harness 侧「选择 Harness → 选择是否使用模板配置 Agent → 填写 Agent 名称 → 进行模型连接并选择模型」。
2. `[推断]` **Qoder 有两条互不相同的接入路径，官方未说明二者关系或如何择一。**
   依据：①`manage-connectors`「当前支持集成 Qoder CLI，即**托管** Qoder 类型的 Agent」（需配站点/组织 ID/API 密钥/服务账号，密钥换取 SAT 存 Vault）②`guidelines-for-the-use-of-local-nanoagent`「适用于 Claude Code、Codex、OpenClaw 和 **Qoder CLI**」（Agent 进程运行在自有机器，由 LoongSuite Pilot 管理，且 **Qoder CLI 不支持平台模型**）。
   → 对客被问「Qoder 怎么接进 AgentCore」时，**必须先问清是要托管还是纳管本地进程**，不得给单一答案。

**选型阶段必须先确认的 5 个客户侧前置条件**（均为逐字原文）[官方]：
1. 是否已开启 **Team 协作** —— 未开启则**控制台不允许创建本地纳管 Agent**
2. VPC 是否满足 **≥2 交换机、覆盖 ≥2 可用区** —— 绑 VPC 时的必填校验
3. 是否具备**企业版 ACR** 实例，且能接受**仓库设为公开 + 开启公开匿名拉取** —— 高代码路径硬要求
4. 镜像是否 **`linux/amd64`** 且**同时提供 `/bin/bash` 与 `/bin/sh`** —— 高代码路径硬要求
5. 本地运行时版本是否达标（Claude Code ≥2.1.141 / Codex ≥0.103 / OpenClaw ≥2026.5.12（Win ≥2026.6.11）/ Qoder CLI ≥1.0.33）—— 本地纳管路径硬要求，且「版本要求可能随产品升级调整」

### 4.8 SA 报价速查（结论层）

> 下列第 2~9 条的月费均由 §4.3 官方换算式**直接推导**，标 `[推断]` 并附算式；**月长统一取官方自己用的 720 小时**。第 1、10~13 条为官方口径或纪律。

1. **先定地域，再问能不能报价**。中国内地 4 地域（北京/杭州/上海/深圳）完全同价，这一项不用纠结；但客户一落新加坡 `ap-southeast-1`，**报价直接做不了**（§4.4）。[官方]
2. **`1 vCPU + 2 GB` 常驻 1 个月 ≈ 359.8 元**。[推断] 算式：官方算例 0.4997 元/小时 × 720 小时 = **359.784 元/月**；按未取整单价精确计算 7200 CU × 0.0000694 元/CU × 720 h = **359.7696 元/月**。本页统一取 **≈359.8 元/月**（两种口径差 **0.014 元**，源自官方对单小时值的四舍五入）。⚠️ 这是**换算推导值，不是官方档位价**（RULINGS B5），报价单要写「按官方换算式推导，实际以控制台所选 CPU/内存与账单为准」。
3. **单价锚：算力 0.2498 元/(vCPU·h)、内存 0.1249 元/(GB·h)**。[推断] 算式：①官方「1 vCPU × 1 小时 = 3600 CU = CNY 0.2498」②「1 GB 内存 × 1 秒 = 0.5 CU」→ 1 GB × 3600 秒 × 0.5 = 1800 CU × 0.0000694 = 0.124920 元。→ **官方换算下「2 GB 内存的价 = 1 vCPU 的价」**，内存密集型 Agent（大内存小 CPU）在成本上不占便宜，选型时别把「加内存不加核」当降本手段。
4. **🔴 协作专享管控面 2160 元/月，是 1vCPU+2GB Agent 常驻算力（359.8 元）的 6.0 倍**。[推断] 算式：官方「CNY 3/小时」× 720 h = 2160 元；2160 ÷ 359.784 = 6.003。→ **开通 Team 协作 = 月账单凭空多一个四位数固定项**，且计费维度是「实例/小时」而非用量，属于开着就烧、不用也烧。**限免期内是 0 元，但官方只说「活动结束后计费策略另行通知」**，报价单必须写成「2160 元/月（2026-10-18 后是否恢复官方未承诺）」。
5. **存储基本可以忽略**：10 GB/月 = **1.8 元**（官方算例原值）；100 GB/月 = 18 元、1000 GB/月 = 180 元。[推断] 算式：GB × 720 h × 0.00025。→ 客户纠结「Agent 记忆库/知识库存储费」时，量级上它排不进前三。
6. **网关按次数看也极便宜，但基数是「连接时长」不是「消息条数」**：官方 0.015 元/万次 → 100 万次 = 1.5 元、1 亿次 = 150 元。[推断] 算式：次数 × 0.0000015。🔴 **长连接按每 30 秒折 1 次**（官方规则），所以：一个保持 24 小时的长连接 = 2880 次 = 0.00432 元；**100 条并发长连接常驻 1 个月 = 864 万次 = 12.96 元**。[推断] 算式：2880 次/天 × 30 天 × 100 条 × 0.0000015。→ 流式输出/MCP 长连接/Agent 长会话场景，网关费的驱动因子是**连接存活时长 × 并发数**，不是对话轮数。
7. **公网流量 0.8 元/GB 是「隐形第二账单」**：100 GB/月 = 80 元。[推断] 算式：GB × 0.8。→ 在轻用量场景下 80 元 > 存储 1.8 元 + 网关 1.5 元 之和，**且它由 CDT 出账、不在 AgentCore 账单里**（§4.2 第 4 条）。客户对账时最容易漏的就是这一项。
8. **一个「最小可算」的组合月账单模板**（内地地域、720 h/月，[推断]，各行算式见上）：

| 计费项 | 假设用量 | 算式 | 月费 |
|---|---|---|---|
| 算力 CU | 1 vCPU + 2 GB 常驻 720 h | 7200 CU/h × 720 h × 0.0000694 | **359.78 元** |
| 存储 CU | 10 GB 常驻 | 10 × 720 × 0.00025 | **1.80 元**（官方算例原值） |
| 网关 CU | 100 万次短请求 | 1,000,000 × 0.0000015 | **1.50 元** |
| 公网流量 | 100 GB | 100 × 0.8 | **80.00 元**（CDT 出账） |
| **小计（不开协作）** | | | **443.08 元** |
| 协作专享管控面（可选） | 1 实例 × 720 h | 720 × 3 | **+2160.00 元** |
| **合计（开协作，限免结束后口径）** | | | **2603.08 元** |

**已知限制（官方，逐条）**：
- **Anthropic 模型返回其对应协议数据结构，不应使用 `choices` 解析**。
- OpenAI/v1 连接可用 `responses()` / `responses_stream()`，**实际模型必须支持 Responses API**，「**SDK 不会在调用失败时自动切换为 Chat Completions**」。
- 「**当前托管模型客户端不提供 Embedding 调用**」；自定义模型客户端的 `embedding()` **仅适用于支持向量生成的服务和模型**。
- 「**模型调用本身不会自动执行 MCP 工具**」；「**加载 Skill 不等于执行 Skill**」，不需要命令执行时设 **`ALLOW_EXECUTE_COMMAND=false`**，**Skill 依赖需包含在应用运行环境中**。
- **MCP headers 是客户端级固定配置**（作用于握手、工具发现和调用），**不是每请求用户身份参数**；Header 名**大小写不敏感**；平台/凭证/自定义 Header **冲突时报错不覆盖**；**不能覆盖 `Authorization`**，**不能手动设置 `Host`、`Mcp-Session-Id`**；SDK **不会自动复制全部入站 Header**。
- **记忆**：新写入**可能有延迟才可检索**；范围字段是**逻辑分区**，「**不是访问凭证或权限校验的替代品**」，应由**可信业务上下文**提供；**多用户应用应显式传范围**。
- 「**CrewAI 完整事件入口需要 CrewAI 1.15.20 及以上版本；其轨迹在执行完成后输出，不是逐 Token 实时输出。**」
- **相同会话 ID 不会自动恢复历史**；**SDK 默认不放开跨域**（CORS 由应用或网关配置）。
- **AG-UI 请求中 `tools: []` 不会禁用 Agent 代码中已配置的工具**；**每次运行用新 `runId`**。

🔴 **两处最容易读漏的限定**：① 失败请求口径把 **4XX 与 5XX 并列**，限定词只有「因 AgentCore Agent 运行时系统原因导致的」——**协议未细分**客户参数错误 / 鉴权失败这类客户侧 4XX 是否计入（`缺口`）；② 赔偿基数是「**出账金额**」且**不含**代金券 / 优惠券 / 赠送额度抵扣部分 → 客户用券抵扣得越多，可赔基数越小。[官方]

### 7.4 赔偿方案（3 档表 + 基数 / 上限 / 形式）

协议 §3.1 引子逐字：「以未达标服务单元（Workspace）的月度服务费用为基数，按当月服务可用性落入的档位计算赔偿：」

| 月度服务可用性 | 赔偿比例（月度服务费用 ×） |
|---|---|
| ≥ 99.0% 且 < 99.9% | **15%** |
| ≥ 95.0% 且 < 99.0% | **30%** |
| < 95.0% | **100%** |

赔偿上限与发放形式（§3.1 逐字）：

> 「赔偿上限：单一服务单元（Workspace）单月累计赔偿**不超过该服务单元当月月度服务费用的 100%**；**不同服务单元分别计算、可叠加**。赔偿以**服务代金券**形式发放，仅可抵扣 AgentCore 后续账单，**不可提现、转让或折现**。」

[官方] 三个要点：① 上限是「单一 Workspace 单月 ≤100% 月费」；② **跨 Workspace 可叠加**（这是 AgentCore 相对「按产品当月服务费封顶」的通用口径更有利的一点）；③ 赔偿**只能是代金券**，无现金救济。

- `[推断]` 「跨 Workspace 可叠加」优于 `service-availability.md` ① 层所述通用口径「赔偿上限（通常为该产品当月服务费）」。依据：① 协议 §3.1 逐字「不同服务单元分别计算、可叠加」② `service-availability.md` line 19 逐字「赔偿上限（通常为该产品当月服务费）」。仅作对照观察，**协议未做任何与通用口径的比较声明**。
- `缺口`：代金券**面额单位、有效期、使用限制**协议未提及（`有效期` 命中 0）；赔偿是否可与商务折让叠加未提及（协议只说跨 Workspace 可叠加，非跨协议）。

### 8.1 服务关联角色（SLR）—— 含 🔴 排障要点

- 定义（逐字）：「服务关联角色（Service Linked Role，SLR）是 AgentCore 在阿里云访问控制 RAM 中**预定义的角色**，用于授权 AgentCore 访问其所依赖的其他云服务。」[官方]
- 🔴 硬前提（逐字）：「**首次使用 AgentCore 前必须完成服务关联角色的创建，否则 AgentCore 服务无法正常运行**。」[官方]
- **角色名（唯一）**：`AliyunServiceRoleForAgentCore`。[官方]
- 🔴 **排障要点 1（最容易踩）**：在 RAM 控制台验证角色时，「在搜索框中输入 **`Magic`** 并搜索」——**搜 AgentCore 搜不到**。[官方]
- 🔴 **排障要点 2**：AgentCore 的云服务 **ServiceName = `magic.aliyuncs.com`**（出自策略内 `ram:DeleteServiceLinkedRole` 的 `Condition`；页面**未以文字明说**，是从 Condition 逐字读出）。另一条 `ram:CreateServiceLinkedRole` 的 Condition 为 `ram:ServiceName = privatelink.aliyuncs.com`。[官方]
- 🔴 **排障要点 3**：OSS 权限**分两层**——Bucket 级（PutBucket / ListBuckets / GetBucketAcl / PutBucketTagging 等）Resource 为 `*`；**对象级**（GetObject / PutObject / DeleteObject / ListObjects / RestoreObject 等 11 条）Resource 逐字硬限定为 **`acs:oss:*:*:hiclaw-*`**，即**只能操作 Bucket 名以 `hiclaw-` 开头的 Bucket**。客户排查「AgentCore 读不到我的 OSS 文件」时先看 Bucket 名前缀。[官方]
- 🔴 **排障要点 4（删除角色的前置条件，逐字 2 条）**：「AgentCore workspace 下**无运行中的 Agent**。」／「**没有依赖该角色的其他资源**。」删除警告：「删除服务关联角色后，AgentCore 服务将无法正常运行。如需重新使用 AgentCore，须再次创建服务关联角色。请谨慎操作。」[官方]
- 创建路径（5 步骨架）：登录 AgentCore 控制台 → 页面提示**授权服务关联角色** → 单击**立即授权** → 按提示**开通依赖云产品**后点**刷新** → 角色创建成功后自动跳转控制台首页。首次访问控制台时「系统会**自动检测**服务关联角色是否存在」。[官方]
- 应用场景（逐字）：「允许 AgentCore 操作**安全组、OSS、AI网关**等云产品的操作，以便完成 AgentCore 实例的相关配置。」[官方]

> 本节是主控在三路蒸馏员草稿 + 客观基线之上亲撰的**判断层**。凡属推理均标 `[推断]` 并附依据；凡官方文档未做横向对比的，**不编造竞品结论**。

### 10.1 适用与不适用

**适用** `[推断]`（依据：§2 资源对象模型 + §3 三种部署形态 + §5 协作与 IM 接入均有官方正文）：
1. 要把**已存在的 Agent 资产**（自研代码 / 本地已部署 Agent）纳入统一平台做**治理、可观测、协作与渠道分发**，而不是从零写 Agent 逻辑
2. 需要**企业级多人协作**：Team/角色/成员权限 + 定时任务 + 通过钉钉/飞书把 Agent 递给业务人员对话式调用
3. 需要**统一的工具与密钥治理**：MCP Server 接入 + 凭证集中管理 + Skill 广场导入 + 模型配置统一切换
4. 需要**平台侧可观测**：Trace 上报到客户自己账号下的云监控 2.0 工作空间

**不适用 / 需另配** `[推断]`：
1. 🔴 **需要企业目录同步（LDAP/SCIM/AD）** → AgentCore 用户认证仅「本地账号」+ 钉钉/飞书扫码，**无目录同步**（§5 缺口），需另配 IDaaS，且 **KB 内暂无 IDaaS 产品卡**（待补登记见 §11.6）
2. 🔴 **超过 30 人的扫码登录场景** → 钉钉/飞书账号集成「**最多支持 30 个用户，超出后账号集成将失败**」`[官方]`，企业级规模会直接走不通，须提前设计（改用本地账号批量建号？官方未给路径 → 缺口）
3. **需要微信生态登录** → 无微信账号集成页（§11.3 N2）
4. **强 SLA 依赖的核心生产链路** → 99.9% 承诺**仅覆盖平台自身的 Agent 运行时服务**，客户自建/第三方 Agent 自身可用性**不在保障内**（§7）
5. **需要明确全成本上限** → 「数据处理量」有计费名目无单价、算力 CU 无规格档位、新加坡无单价（§11.2）

### 10.4 实操避坑清单（来自官方正文，非经验推测）

1. 🔴 **`--` 之后的运行时参数是「整体替换」语义** —— 改并发数会**冲掉**继承的开关与命令路径参数。改任何一项都要把整串参数重写全 `[官方]`（§3）
2. 🔴 **健康检查端口与服务端口不匹配会触发实例重启** —— 部署高代码 Agent 时两个端口必须对齐 `[官方]`（§3）
3. **本地纳管 Agent 生成的文件不会自动上传到 Team** —— 需要产物回流的话要自己实现 `[官方]`（§3）
4. **Skill 发布前有强制安全检测** —— 排期时留出检测时间，不要承诺「即时发布」 `[官方]`（§2）
5. 🔴 **Skill 配置文件名官方口径不一致**：`Skills.md` vs `SKILL.md`；另 `SOUL.md` / `AGENT.md` / `AGENTS.md` 三页并存（§11.3 N8）—— **文件名大小写在 Linux 下敏感**，实操**以控制台实际生成的文件名为准**，不要照文档手敲
6. **高代码 Agent 要求公开可访问的镜像仓库**（或按 ACR 侧网络白名单放通）—— 客户内网镜像仓库场景要提前设计 `[官方]`（§3）
7. 🔴 **RAM 控制台验证服务关联角色要搜 `Magic` 而不是 AgentCore**；ServiceName = `magic.aliyuncs.com`；OSS 对象级权限硬限定 `acs:oss:*:*:hiclaw-*`；**删除角色前须 Workspace 下无运行中 Agent**（§8）。⚠️ `Magic` / `hiclaw` 是**产品内部代号，对客慎用**（暴露内部命名），仅用于内部排障定位
8. **IM 渠道接入是权限外溢面**：官方安全注意逐字「IM 用户可使用该 Agent 已配置的模型、Skill、MCP 工具和凭证能力；**群内可 @机器人 的成员都可能调用该 Agent**」`[官方]`（§5）→ 把 Agent 拉进大群等于把它的凭证能力开放给全群，**方案设计时必须做群成员治理**
9. **IM 接入需放通 6 个白名单 IP**（`121.40.82.220` 等，完整清单见 §5）—— 客户有出网管控时要提前报备
10. **协作服务高可用要求 ≥2 个不同可用区的交换机** —— Workspace 绑 VPC 时「请至少选择两个不同可用区的交换机」`[官方]`（§2）

### 10.5 报价速查（指针）

完整表与算式在 **§4**，与 `references/pricing-verification-checklist.md` 已逐项对齐（C1/C2/C3/C4/C8/C9/C13/C14）。三条最常被问的量级：

| 场景 | 量级 | 算式（官方换算式直接推导） |
|---|---|---|
| 1 vCPU + 2 GB 常驻 1 个月 | **≈359.8 元/月** `[推断]` | 官方算例 0.4997 元/小时 × 720 小时 = **359.784 元/月**；按未取整单价精确计算 7200 CU × 0.0000694 元/CU × 720 h = **359.7696 元/月**。本页统一取 **≈359.8 元/月**（两种口径差 **0.014 元**，源自官方对单小时值的四舍五入） |
| 协作专享管控面 1 个月 | **2160 元/月**（限免期 0 元）`[推断]` | 3 元/h × 720 h；🔴 是上面算力的 **6.0 倍**，属门槛费型（checklist C13） |
| 10 GB 存储 1 个月 | **1.8 元/月** `[官方]` | 官方算例逐字：10 × 720 = 7200 CU × 0.00025 = 1.8 元 |

🔴 **报价前必做**：① 确认客户地域是否在已公开价的四地内（§11.2）；② 叠加 **3 个依赖产品**费用（云监控 CMS / PrivateLink / SchedulerX3）—— **AgentCore 账单 ≠ 全成本**；③ 复核限免是否已结束（§0 横幅）。

### 12.2 抓取通道与方法沉淀（♻️ 可复用到任何 help.aliyun.com 产品蒸馏）

#### 闸 2：独立模型族交叉评审（qodercli + Kimi-K3）

**为什么用 Kimi-K3**：本页由 Qoder 系 agent（主控 + 7 路 subagent）蒸馏，评审必须换**模型族**，否则同族盲区会被复制多遍。

**方法**：以 `raw/` 为唯一权威基线，给**缺陷分类表**（F1 幻觉事实 / F2 数字·单位·日期错 / F3 限定词丢失 / F4 证据标注错档 / F5 表格失真 / F6 死链 / F7 缺口未声明 / F8 时效锚缺失 / F9 内部口径分叉 / F10 危险性靠遗漏）而非问「对不对」；12 组承重断言定点核实（V1~V12）+ 5 项附加扫描（S1~S5）；纪律要求**任何不利判定必须附 raw 逐字反证与行号**，贴不出只能判 UNVERIFIABLE；禁止联网、禁止采信被测页面的自我声明。

**🔴 负控实验（评审闸的校准，与闸 1 同理）**：另起一路**完全相同的核查书**（仅被测页路径不同），跑一份**注入了 5 类伪造错误的副本**（算力单价少一个零 / SLA 抬到 99.95% / 用户上限改 300 / 限免截止日延后 2 个月 / 回收阈值放宽到 90 天）。
结果：**5/5 全部被抓出，全部定级 CRITICAL，定位到节与行**。
→ **这证明评审闸是活的**：它不是因为页面干净才报少，而是真的具备检出能力。没有这一步，「只有 4 条缺陷」这个结论毫无意义。

**真页评审结果**：V1~V12 中 **10 组判 OK**（5 个计费项单价、CU 换算与算例、地域价表、限免窗口全部边界、SLA 全部数字与两条限定词、限免期 SLA 推断、6 条硬配额、账号集成上限与 IM 清单、AgentTeams 迁移事实均**逐字命中 raw**），2 组判 F2。共报 **4 条缺陷**。

#### 闸 2 补充：fix-verification 轮（修订后复核，**不重跑全量评审**）

修复落地后**不重跑全量评审**（4 条真信号会淹没在 90+ 无争议条目里），而是起第三路 Kimi-K3，输入只含「被标项 + 旧值 + 主控裁决的新值」三件套，判定词汇限定为闭集 `PASS-FIXED / STILL-ISSUE / NEW-ISSUE`，且判 STILL/NEW **必须逐字引用页面当前原文 + 行号**。
