### 8.1 MCP 接入形态总览与选型判据

AI 网关 MCP 服务管理"提供 RESTful API 至 MCP 服务的平滑迁移能力，支持 SSE、Streamable HTTP 两种协议访问，并集成基于消费者身份的鉴权认证机制" [官方原文｜gateway-managed-mcp-services｜mcp-gateway-management｜mcp-service-management]。

| 形态 | 后端要求 | 传输/协议 | 工具从哪来 | 卡片标识 | 主要适用场景 | 来源 slug |
|---|---|---|---|---|---|---|
| **MCP 直接代理** | 后端原生是 MCP Server | **MCP Transport 支持 SSE 和 Streamable HTTP 两种传输协议** | 后端自带，网关不组装 | "直接代理" | "适用于原生支持 MCP 协议的服务。该模式能够实现高效的流式通信和上下文保持，特别适合高并发、长连接的场景，例如 AI 推理、多模型协同等" | gateway-managed-mcp-services |
| **HTTP 转 MCP** | 后端是 HTTP Server | 对外同时暴露 SSE 与 Streamable HTTP 两个接入点路径 | Swagger/OpenAPI 导入 或 自定义 YAML | "HTTP转MCP" | 存量 RESTful API 平滑迁移为 MCP 工具 | gateway-managed-mcp-services、http-to-mcp-field-configurations |
| **Nacos 同步** | 服务已注册在 MSE Nacos | 由 Nacos 侧协议类型决定：`mcp-sse` / `mcp-streamable` / `http` | 随 Nacos 服务同步 | 在"直接代理"或"HTTP转MCP"标识外**新增"Nacos托管"标识** | "通过 Nacos 提供的 MCP Router 功能，实现服务注册发现及协议自动转换，支持存量 HTTP 服务"零改动"升级为 MCP 协议接口" | synchronizing-nacos-mcp-services、mcp-service-management |
| **虚拟 MCP 服务（Tool 组装）** | 无独立后端，聚合已有 MCP 服务 | [文档未说明] | 从多个已有 MCP 服务挑选工具聚合 | [文档未说明] | "在同一个虚拟MCP服务中添加来自多个MCP服务的工具，实现统一的MCP服务入口，避免分散管理多个MCP Server的复杂性" | mcp-tool-assembly |

**选型判据（SA 可直接引用）**

- 客户已有 MCP Server → **直接代理**。选型的关键差异在于**工具级授权行为**：直接代理下无权限工具仍会出现在 `tools/list`（见 §8.10 逐字引用），只有调用时才 403。若客户要求"未授权工具对模型不可见"，直接代理不满足。
- 客户只有 REST API、不想改代码 → **HTTP 转 MCP**。此形态下工具列表会按授权过滤，模型只看得到有权限的工具。代价是必须为每个接口写 tool 定义（Swagger 自动生成或手写 YAML），且参数取值位置有限制（见 §8.4.7）。
- 客户已用 MSE Nacos 做注册中心 → **Nacos 同步**，避免在网关侧重复维护服务清单。硬门槛：MSE Nacos 3.0 及以上 + **网关引擎版本 2.1.6 及以上**（版本口径存在官方矛盾，见 §8.6）。
- 客户有几十上百个 MCP Server、要给 Agent 一个统一入口 → **虚拟 MCP 服务**做聚合；工具数量大导致模型选不准时再叠加 **语义检索**（§8.8）或 **工具精选**（§8.9）。

### 8.2 MCP 直接代理

创建路径：实例 → **MCP 管理** → **创建MCP服务** → 协议选 **MCP**（"若后端为MCP Server，则选择MCP协议"）[官方｜gateway-managed-mcp-services]。

| 配置块 | 字段 | 说明（官方原文要点） |
|---|---|---|
| 后端服务 | 服务名称 | 选择已有服务 |
| 后端服务 | 服务协议 | 选 **MCP** |
| 后端服务 | **MCP Transport** | "按需选择**MCP Transport**，支持SSE和Streamable HTTP两种传输协议。" |
| 后端服务 | 路径 | "路径是实际的后端mcp server的访问path。比如后端mcp server访问端点是xxx.com/sse，路径就填/sse；如果是xxx.com/test/sse，路径就填/test/sse。" |

### 8.3 HTTP 转 MCP

创建路径：协议选 **HTTP 转 MCP**（"若后端为HTTP Server，则选择HTTP转MCP协议"）[官方｜gateway-managed-mcp-services]。

| 配置块 | 字段 | 必填 | 说明 |
|---|---|---|---|
| 后端服务 | 服务名称 | 是 | "选择**服务名称** 并选择**服务协议**为HTTP。若您没有创建服务，需要新建服务，建议您使用FC或者DNS这类服务进行测试。" |
| 后端服务 | **描述** | **是（必填）** | "描述是必填项，该字段表示MCP工具的功能用途，以提升API的可理解性和AI处理的准确性。" |
| MCP 接入点 | 域名 | 是 | 支持选择多个域名 |
| MCP 接入点 | 路径 (SSE) | — | "通过/mcp-servers、/MCP服务名称以及/sse拼接而成。" |
| MCP 接入点 | 路径 (Streamable HTTP) | — | "通过/mcp-servers和MCP服务名称拼接成的。" |

**🔴 与直接代理的关键差异**：HTTP 转 MCP 对外**同时**给出 SSE 与 Streamable HTTP 两个接入点路径，且路径规则不同（SSE 带 `/sse` 后缀，Streamable HTTP 不带）；直接代理只有一个由后端 path 拼接而成的接入点 [官方｜gateway-managed-mcp-services]。

**灰度发布形态限制**：MCP 服务灰度发布文档给出的操作步骤是"**协议** 选择**HTTP转MCP**，使用场景选择按比例（多服务）" [官方｜mcp-grayscale-release]。直接代理形态是否支持灰度 → [文档未说明]。

> 🔴 **互斥与优先级规则（客户对接必查，均为官方原文）**
> 1. **请求体四选一**：`body` / `argsToJsonBody` / `argsToUrlParam` / `argsToFormBody`。"请注意，这四个选项是互斥的，在一个工具配置中只能使用其中一种。**如果同时配置了多个选项，系统会报错并拒绝加载该工具配置。**"
> 2. **响应体三选一**：`responseTemplate.body` 与 `prependBody` / `appendBody` 互斥（`prependBody` 与 `appendBody` 可同时用，二者均只声明"与`body`互斥"）。
> 3. **`position` 优先于批量选项**："当使用 `position` 指定参数位置时，这些参数将按照指定的位置处理，而不会受到批量参数处理选项（`argsToJsonBody`、`argsToUrlParam`、`argsToFormBody`）的影响。**只有未指定 `position` 的参数才会受到这些批量选项的影响。**"
> 4. **显式 `body` 会吞掉 `position: body`**："如果在 `requestTemplate` 中明确指定了 `body`，则所有 `position: body` 的参数都将被忽略，以避免冲突。"

#### 8.4.4 参数位置（`position`）与批量处理方式

| `position` 取值 | 行为 |
|---|---|
| `query` | "参数将作为查询参数添加到 URL 中。" |
| `path` | "参数将替换 URL 中的路径占位符，例如 `/pet/{petId}` 中的 `{petId}`。" |
| `header` | "参数将作为 HTTP 头添加到请求中。" |
| `cookie` | "参数将作为 Cookie 添加到请求中。" |
| `body` | "参数将添加到请求体中（根据内容类型自动格式化为 JSON 或表单）。" |

四种批量参数处理方式（**互斥，只能选一种**）：

| 方式 | 行为（含自动 Header） |
|---|---|
| `body` | "使用模板手动构建请求体。这是最灵活的方式，允许您完全控制请求体的格式。" |
| `argsToJsonBody: true` | "未指定 `position` 的参数将直接作为 JSON 对象发送到请求体中，并**自动添加 `Content-Type: application/json; charset=utf-8` 头**。" |
| `argsToUrlParam: true` | "未指定 `position` 的参数将作为查询参数添加到 URL 中。" |
| `argsToFormBody: true` | "未指定 `position` 的参数将以 `application/x-www-form-urlencoded` 格式编码在请求体中，并**自动添加相应的 Content-Type 头**。" |

**参数类型语义**：`string`（默认）、`number`（浮点数）、`integer`（整数）、`boolean`（true/false）、`array`（用 `items` 定义元素模式）、`object`（用 `properties` 定义属性模式）[官方｜http-to-mcp-field-configurations]。

#### 8.4.5 认证与安全：`server.securitySchemes[]`

| 字段 | 数据类型 | 必填 | 取值范围 | 描述（官方原文） |
|---|---|---|---|---|
| `id` | string | **必填** | [未给] | "认证方案的唯一标识符，供工具配置引用。" |
| `type` | string | **必填** | `http`（用于 Basic 和 Bearer 认证）、`apiKey` | "认证类型。" |
| `scheme` | string | 选填 | `basic` 或 `bearer` | "当`type`为`http`时指定具体的方案。" |
| `in` | string | 选填 | `header` 或 `query` | "当`type`为`apiKey`时指定 API 密钥的位置。" |
| `name` | string | 选填 | [未给] | "当`type`为`apiKey`时指定 Header 名称或查询参数名称。" |
| `defaultCredential` | string | 选填 | [未给] | "此方案的默认凭证。例如，对于Basic Auth，可以是`user: password`；对于Bearer Token，是Token本身；对于API Key，是 Key本身。" |

**两级认证的作用域必须分清**（这是客户最常配错的地方）：

| 配置节点 | 管的是哪一段链路 |
|---|---|
| `tools[].security.id` | **MCP Client ↔ MCP Server**。"插件将根据此方案从客户端请求中提取凭证，并**清理原始请求中的该凭证**。" |
| `tools[].requestTemplate.security.id` | **MCP Server ↔ 后端 HTTP API**。 |

**透明认证（Passthrough）工作流程**（官方给出 6 步，以 Client 用 Bearer、后端用 API Key 为例）[官方｜http-to-mcp-field-configurations]：

1. MCP Client 请求工具，`Authorization` 头携带 `Bearer <client_token>`。
2. MCP Server 按 `tools[].security`（如 `ClientSideBearer`）识别凭证类型，"从请求中提取 `<client_token>` 并**移除原始的 `Authorization` 头**"。
3. 因 `passthrough: true`，提取出的凭证被标记为透传凭证。
4. MCP Server 调后端时读取 `requestTemplate.security`（如 `BackendApiKey`）。
5. "MCP Server 将之前提取的 `<client_token>` 作为凭证值，按照 `BackendApiKey` 方案（即作为名为 `X-API-Key` 的 HTTP Header）添加到对 `https://api.example.com/products/...` 的请求中。"
6. 后端收到请求，`X-API-Key` 的值即 `<client_token>`。

**透明认证的两条重要约束**（官方原文）：

- "当 `tools[].security.passthrough` 为 `true` 时，`requestTemplate.security.credential` 字段会被忽略，优先使用透传的凭证。"
- "透传的凭证值会直接用于 `requestTemplate.security` 指定的认证方案。**请确保凭证的格式与目标认证方案兼容。** `extractAndRemoveIncomingCredential` 函数会尝试提取核心凭证部分（例如，Bearer token 值，Basic auth 的 base64 编码部分）。"

**🔴 透传凭证不生效的官方三步自查**（客户排障高频，逐条照抄）：

1. **确认工具级别是否已启用透传**：检查 `tools[].security.passthrough` 是否为 `true`。"该字段必须配置在具体工具的 `security` 节点下，**仅在 `server.securitySchemes` 中定义认证方案不会自动启用透传**。"
2. **确认认证方案与客户端凭证类型一致**：`tools[].security.id` 引用的方案的 `type`/`scheme` 需与客户端实际传入的凭证类型匹配（如 Bearer 需 `http`/`bearer`），"否则插件无法从请求中正确提取凭证"。
3. **确认 `defaultCredential` 本身是合法凭证**："透传未生效时，系统会**回退使用** `requestTemplate.security` 对应认证方案下配置的 `defaultCredential`。请确认该值是一个真实可用的凭证（例如合法 JWT 格式的 Bearer Token），不要保留模板占位符或示例值。**`defaultCredential` 格式非法会导致认证校验失败。**"

#### 8.4.6 控制台侧「后端服务认证」的三种方式

创建/添加工具时可"（可选）开启后端服务认证"，控制台提供三种认证方式，官方说明如下 [官方原文｜gateway-managed-mcp-services｜mcp-service-management]：

| 参数 | 说明（官方原文） |
|---|---|
| **Basic** | "将用户名和密码以username: password的形式进行Base64编码后，放在HTTP请求头的Authorization字段中发送。" |
| **Bearer** | "客户端先通过登录接口获取一个令牌，通常是JWT。以后每次请求都在Authorization头中带上该令牌。令牌通常是临时的，可以设置有效期。" |
| **API Key** | "由服务端分配给客户端一个唯一字符串作为访问凭据，客户端在每次请求时通过Header或Query参数提交。" |

#### 8.4.7 模板语法与取值位置约束

- **模板引擎**：`GJSON Template`（`https://github.com/higress-group/gjson_template`），"结合了 Go 的模板语法和 GJSON 的强大路径语法"。
- **请求模板可用变量**：`.config.字段名`（访问配置值）、`.args.参数名`（访问工具参数）。
- **响应模板**：GJSON 路径语法访问 JSON 响应字段；模板函数 `add`、`upper`、`lower` 等；控制结构 `if`、`range`、`with`；变量赋值 `{{$var := .value}}`。
- **函数库**："GJSON Template 包含了所有 Sprig 的函数，提供了 **70+ 种**用于字符串操作、数学运算、日期格式化等的模板函数，**功能等同于 Helm 的模板能力**。"
  - 字符串：`trim`、`upper`、`lower`、`replace`、`plural`、`nospace`｜数学：`add`、`sub`、`mul`、`div`、`max`、`min`｜日期：`now`、`date`、`dateInZone`、`dateModify`
  - 列表：`list`、`first`、`last`、`uniq`、`sortAlpha`｜字典：`dict`、`get`、`set`、`hasKey`、`pluck`｜流程控制：`ternary`、`default`、`empty`、`coalesce`
  - 类型转换：`toString`、`toJson`、`toPrettyJson`、`toRawJson`｜编码/解码：`b64enc`、`b64dec`、`urlquery`、`urlqueryescape`｜UUID：`uuidv4`
- **GJSON 路径语法**：点表示法 `address.city`；数组索引 `users.0.name`；数组迭代 `users.#.name`；数组过滤 `users.#(age>=30)#.name`；修饰符 `users.@reverse.#.name`；多路径 `{name:users.0.name,count:users.#}`；转义 `path.with\.dot`。复杂查询用 `gjson` 函数。
- 🔴 **`tools[].args` 的定位（官方原文）**："`tools[].args`参数用于定义AI网关在接收MCP请求参数后，将其转换并组装为HTTP请求的规范，具体描述了发送至后端服务的HTTP请求中各参数的属性，包括参数类型、参数位置（如路径、请求头、请求体）以及是否为必填参数。"
- 🔴 **取值位置限制（官方原文，最容易踩）**："AI网关接收到MCP请求后，将根据MCP协议规范从请求体对应位置提取参数，**暂不支持从其余位置（如请求头，请求体中其他位置）提取参数**。"
  - [推断] 由该句 + `position` 字段语义推出：`position` 控制的是**网关→后端**这一跳的参数落位，而**Client→网关**这一跳的参数只能来自 MCP 协议规定的请求体位置。因此想从入站 Header 取值做工具参数，YAML 层面做不到。
- **内置 MCP 服务器**：`server.name` 填内置服务器名（示例 `quark-search`）即可，"无需配置 tools 字段，因为工具已经在服务器中预定义好了"，配置项形如 `server.config.apiKey`。

### 8.8 MCP 语义检索

#### 8.8.1 解决什么问题

"当用户开发的智能体需要调用大量MCP工具时，可能面临**管理困难、工具选择不合适、Tokens消耗增加以及检索效率降低**等问题。" [官方原文｜semantic-retrieval]
一句话定位："语义检索可基于用户请求，通过分析理解用户意图，智能选择合适的MCP工具，从而**降低上下文Token，提升检索效率**。"

#### 8.8.2 五个能力要点

| 要点 | 官方描述（要点摘录） |
|---|---|
| 统一入口管理 | "通过AI网关构建统一的MCP服务接入点，所有Agent可通过**单一端点**访问网关实例中注册的**全部MCP工具**" |
| 智能工具检索 | "集成 **`x_higress_tool_search`** 语义搜索功能，基于 **AD向量数据库**[原文如此] 与 **Qwen系列大模型**…Agent可通过自然语言描述需求，系统自动匹配并返回最相关的工具，**无需预先了解具体工具名称**" |
| 双阶段检索机制 | "**向量召回 + 重排序**两阶段检索架构。首先利用 **Qwen Embedding** 模型进行向量化相似度计算，获取初步候选工具集，然后**可选择性地**使用 **Qwen Rerank** 模型对候选结果进行精细化排序" |
| 实时元数据同步 | "当用户在控制台执行MCP Server的**增、删、改**操作时，系统自动触发工具元信息的采集、向量化处理及持久化存储，确保向量数据库与实际部署的服务实例保持一致" |
| 控制台集成化配置 | "在控制台启用"语义搜索"功能后，系统将自动完成 **ADB集合初始化、模型参数配置、路由规则下发及数据同步** 等全部配置流程" |

> 🔴 **[官方矛盾]（同页两处，产品名不一致）**：一处写"基于 **AD向量数据库**"，另一处写"系统将自动完成 **ADB集合初始化**"（疑为 ADB/AnalyticDB 缩写笔误）。不裁决，SA 对客建议只说"向量数据库"，产品名以购买页/控制台为准。

#### 8.8.3 配置步骤与鉴权限制

- **启用**：MCP 管理 → **语义检索** 页签 → **编辑** → 开启 **启用语义检索** → 选择 **检索工具接入点** → **确定** 发布 [官方｜semantic-retrieval]。
  - "检索工具接入点"的 URL 形态、与普通 MCP 接入点的关系 → [文档未说明]。
- **消费者认证**："语义检索支持配置认证鉴权，**开启后仅授权的消费者可通过API Key访问，无认证或认证异常的请求将被拒绝**。" 认证方式**默认选择 API KEY**。
- 🔴 **硬限制（官方原文）**："消费者认证方式需使用API Key，**不支持JWT认证方式的消费者使用语义检索**。"

#### 8.8.4 性能数据（逐字照抄，勿改精度）

评测数据集：Salesforce 的 `xlam-function-calling-60k`。对比 **18 个维度**：纯向量检索 3 种相似度算法（cosine、L2、IP）；RRF 混合搜索双路召回 5 个 k 值（10、30、60、100、200）；Weight 混合搜索 5 个 α 值（0.0、0.2、0.5、0.8、1.0）；Cascaded 混合搜索（无参数算法）；4 种最优配置综合对比 [官方｜semantic-retrieval]。

**融合算法定义（官方原文）**：
- **RRF（倒数排序融合）**："有一个参数 k 控制融合效果，指定计算分数的算法的 **1/(k+rank_i)** 中的 k 常数，范围大于 1 的正整数。"
- **Weight（比重排序）**："采用一个参数 alpha 控制向量和全文的分数比重，然后再排序，计算公式 **alpha \* vector_score + (1-alpha) \* text_score**，参数 alpha 表示向量和全文的检索分数比重，范围为 **0～1**，其中 **0 表示仅全文，1 表示仅向量**。"
- **Cascaded**："先全文检索再在其基础上进行向量检索。"

### 8.9 工具精选策略（Tool Selection）

#### 8.9.1 定位与适用场景

"工具精选策略通过**重排序与可选的查询改写**，在**请求发送至大语言模型前**对工具列表进行预处理和筛选，可提升大规模工具集场景下的响应速度与选择精度，并降低Token成本。" [官方原文｜tool-selection]

| 适用场景 | 官方描述 |
|---|---|
| 大规模工具集管理 | "当开发者构建包含**数十或上百个工具**的复杂Agent时，需确保模型能够高效且准确地进行工具选择。" |
| 多轮对话中的意图识别挑战 | "在连续多轮对话中，用户的核心意图可能分布在历史对话内容中，若仅依据最新输入进行工具匹配，可能导致选择偏差。" |
| Token限制下的优化需求 | "当所有工具的**名称与描述（不含参数）**总长度超出 **Rerank模型的输入Token限制**时，需采用有效的筛选或排序策略以保障功能正常运行。" |

#### 8.9.2 工作流（5 步，执行位置很关键）

"工具精选在**API请求被转发至后端大语言模型服务前**执行"：

1. **请求接收**：AI网关接收包含查询和原始工具列表的 API 请求。
2. **查询改写（可选）**：若启用，"分析对话上下文，对原始查询（Query）进行优化和重写，生成更明确的查询语句，以提升后续工具匹配的准确性"。
3. **工具精排**：接收（可能已被改写的）查询和完整的工具列表，"使用 **Rerank 模型**计算每个工具与查询之间的相关性得分"。
4. **工具筛选**：按预设筛选策略（如 Top-N、Top-K）筛选最优子集，"**相关性得分低于设定阈值的工具将被丢弃**"。
5. **请求转发**："AI网关将原始请求中的工具列表**替换为**筛选后的精简工具列表，然后将请求转发给后端的大语言模型。"

🔴 **硬限制（官方原文）**："此策略**仅适用于工具信息位于请求体 `tools` 字段内的 Function Calling 请求**。"

**配置入口**：AI 网关控制台 → 实例 → 左侧导航 **Model API** → 单击目标 **API名称** 进入 **API详情** → **策略与插件** → 开启 **工具精选** 开关并完成配置 → **保存** [官方｜tool-selection]。
> 🔴 注意：工具精选挂在 **Model API** 上，不是挂在 MCP 服务上。MCP 服务侧能否复用 → [文档未说明]。

#### 8.9.5 官方 FAQ（三条，SA 答疑直接可用）

**Q1：「工具精排」功能相比传统的向量检索有什么优势？为什么它更精准？** 官方答：核心区别在**信息处理的方式**，"这直接决定了其精确度的差异"。
- **传统向量检索（不够精准）**："此方法通常先将"用户查询"和"工具描述"**分开**、独立地转换成数学向量（Embedding），然后再计算这些向量之间的相似度来排序。**局限性**：这个过程是"隔离"的，查询和工具之间缺乏深度的交互。这就像是通过比较两本书的**摘要**来判断它们是否相关，很多细节、上下文和复杂的逻辑关系会丢失，导致对用户真实意图的理解不够深入。"
- **AI网关工具精选的 Rerank 交叉编码器（更精准）**："Rerank模型采用了一种更先进的架构。不会分开处理，而是将**"用户查询"和"工具描述"配对拼接在一起，作为一个整体输入**给模型进行分析。**优势**：这种方式实现了"深度交互"。模型可以直接、细致地分析查询中的每个词与工具描述中每个词的关联。这就像是把两本书**并排放在一起逐页对比阅读**，能够捕捉到复杂的意图、**否定关系**和特定条件。**结果**：因此，Rerank的判断标准从"语义上是否相似"跃升到了"**功能上是否真正匹配**"，能够更精准地理解用户的任务需求，从而筛选出最合适的工具。"

**Q2：查询改写（Query Rewriting）功能推荐开启吗？有什么副作用？** 官方答："在多轮对话的业务场景下，**强烈推荐开启**。"
- **收益**："查询改写能将依赖上下文的模糊、简洁的用户问题，转化为一个**信息完整的独立查询**，极大地提升后续工具精排（Reranking）和最终LLM选择工具的准确性。"
- **副作用**："会引入**一次额外的模型调用**，因此会带来轻微的响应耗时增加。但对于多轮对话场景，增加的耗时换来的准确性提升通常是完全值得的。**如果应用场景均为单轮对话，则可以关闭此功能。**"

**Q3：遇到不符合预期的工具选择结果，应如何解决？** 官方给四条排查优化方向：
1. **优化工具描述**："确保每个工具的名称（name）和描述（description）清晰、准确且具有区分度。**Rerank模型和LLM都强依赖这部分信息**来理解工具的功能。"
2. **自定义查询改写提示词**："如果内置的改写逻辑不完全符合业务需求，可以尝试使用自定义Prompt，设计更贴合场景的改写策略。"
3. **调整筛选参数**："根据实际情况调整Top-N/Top-K的数值。如果发现**正确的工具经常被过滤掉**，可以适当**调高**该值；如果**总是引入不相关的工具**，可以适当**调低**。"
4. **调整相关性得分阈值**："适当提高相关性得分阈值（**如设置为0.3**），可以过滤掉相关性不高的工具，进一步提升工具列表的"信噪比"。"

#### 8.10.2 建连失败的官方 5 条常见原因（专页完整版，逐字）

1. "如果使用的是AI网关提供的测试域名，存在调用限额，**每天整个域名限额1000次**。"

#### 8.10.3 🔴 消费者只授权部分工具时的行为差异（**逐字引用官方原文，客户争议高频点，禁止改写**）

| 未开启消费者认证 / 全量授权 | [文档未说明] | — | — |

> 🔴 **SA 避坑要点**：客户要求"未授权工具对模型完全不可见"（防止模型尝试调用后拿到 403、或防止工具清单泄露内部接口名）时，**必须走 HTTP 转 MCP**；直接代理形态下工具清单对任何持有效凭证的消费者都是**全量可见**的，鉴权只在**调用**环节拦截（403）。这是设计行为，不是 bug。

### 8.11 MCP 服务灰度发布

- **机制（官方原文）**："MCP服务支持配置**多版本后端服务**，并通过配置**服务权重**实现灰度发布。"
- **前提条件（官方原文）**："本方案为**验证**AI网关MCP服务后端服务灰度发布能力，在执行验证前需创建**两个服务**，并确保服务返回结果有**明显差异**，便于验证灰度发布结果。"
  - [推断] 该页整体是**验证性方案**（"本方案为验证…能力"），不是完整功能手册。因此灰度的能力边界（是否支持 Header/消费者维度分流、是否支持直接代理形态、权重取值范围）在此页均无据可依。
- **配置要点**：MCP 管理 → **创建MCP服务** → **协议**选择 **HTTP转MCP** → **使用场景**选择 **按比例（多服务）** → 后端服务中服务名称选已创建的服务来源、**服务权重设置为50** → 单击**添加**完成另一个服务的配置、权重同样设置为 **50** → 完成**描述**与**域名**配置 → **保存并发布**。
- **结果（官方原文）**："本操作步骤执行完，用户将获得一个配置了两个服务版本，且两个版本的路由比重为 **1:1** 的MCP服务。**多服务及权重设置可按场景需要自定义。**"

**官方验证结论（4 条，逐字）**：

| # | 验证场景 | 官方结论 |
|---|---|---|
| 1 | "后端服务配置为单服务" | "多次请求结果均路由至单一版本。" |
| 2 | "后端配置为多服务，服务权重设置中**存在一项为0**" | "多次请求结果**设置为0的服务不会被访问**，其余服务**路由次数比等于服务权重比值**。" |
| 3 | "后端服务配置为多服务，但**仅配置一个后端服务**" | "可正确完成配置并且多次请求结果均路由至单一版本。" |
| 4 | "**同一个后端服务被两个MCP服务使用**，并且其中一个单服务，另一个是多服务" | "此时两个MCP服务均可正常访问。" |

> 🔴 第 4 条对 SA 有价值：**后端服务可被多个 MCP 服务复用**，单服务/多服务配置互不干扰。
> **空白**：权重取值范围、是否支持非整数权重、权重总和是否必须为 100、是否支持按 Header/Query/消费者维度分流、直接代理形态能否灰度、灰度是否影响 MCP 工具列表 → 全部 [文档未说明]。

#### 8.13.1 各策略参数与数字

| 策略 | 关键参数 | 数值/取值范围（逐字） | 备注与限制 |
|---|---|---|---|
| **并发控制** | 是否开启、总体并发数阈值、Web fallback 行为 | Web fallback 的 **Http状态码"默认为429"**；返回 content-type 可选**普通文本**或**JSON** | 原理："统计当前网关处理中的请求数之和，当指标达到设定的阈值时**立即拦截流量**，可配置为后端服务的最大并发处理请求数，实现在高并发下的后端服务可用性保护。" fallback 行为两分支：**返回指定内容**（Http状态码／返回 content-type／HTTP 返回文本）、**返回指定内容 → 跳转地址** |
| **流量控制** | 是否开启、总体QPS阈值、Web fallback 行为 | Http状态码**默认为429**；content-type 同上 | 原理："监控API的**QPS**指标，当指标达到设定的阈值时立即拦截流量，避免后端服务被瞬时的流量高峰冲垮。" fallback 行为两分支：**返回指定内容**、**跳转到指定页面 → 跳转地址** |
| **熔断策略** | 是否开启、统计窗口时长、最小请求数目、阈值类型、慢调用RT、熔断比例阈值、熔断时长(s)、Web fallback | **统计窗口时长"取值范围为1秒\~120分钟"**；**熔断比例阈值"取值范围 0-100（代表 0%-100%）"**；Http状态码**默认为429** | 阈值类型二选一：**慢调用比例（%）** 或 **异常比例（%）**。最小请求数目："若当前统计窗口内的请求数小于此值，**即使达到熔断条件规则也不会触发**"。慢调用路径："在单位统计时长内请求数目大于设置的最小请求数目，并且慢调用的比例大于阈值，则接下来的熔断时长内请求会自动被熔断。**经过熔断时长后，熔断器会进入探测恢复状态，若接下来的一个请求响应时间小于设置的慢调用RT，则结束熔断；若大于设置的慢调用RT，则会再次被熔断。**" 异常比例路径："在单位统计时长内业务异常数目大于设置的最小请求数目，并且异常的比例大于阈值，则接下来的熔断时长内请求会自动被熔断。" 熔断时长(s)："资源进入熔断状态后，在配置的熔断时长内，请求都会**快速失败**。" |
| **IP黑白名单** | 开启、名称、备注、类型、IP地址/地址段 | 格式示例 `192.168.1.1/24`，"支持多个条目" | **白名单**："仅允许指定的 IP 地址访问服务，**其余默认拒绝**"；**黑名单**："阻止特定 IP 地址访问服务，**其余默认允许**"。名称："自定义标识名称，用于在多个策略中进行区分和管理。" |
| **超时** | 开启、超时时间 | 单位**秒** | 🔴 "当设置为**0**或者关闭超时策略时，表示网关会**一直等待**请求的响应结果。" 超时后"向客户端返回一个 HTTP 状态码为 **504（Gateway Timeout）** 的响应结果"。官方"说明"："超时策略配置完成且开启后，请根据实际业务**验证**服务超时规则是否生效。" |
| **Header修改** | 开启、Header类型（请求/响应）、操作类型（新增/修改/删除）、Header Key、Header Value | — | **新增**："如果新增的Header已存在，那么Header Value将会**拼接在已有的Header值后面，并通过英文逗号（,）分隔**"；**修改**："如果指定的Header不存在，将会按照Header Key和Header Value进行**新增**操作；如果指定的Header存在，将会进行**覆盖修改**操作"；**删除**："删除请求或响应指定的Header。" 作用时机："在将请求转发至目标后端服务之前，或在后端服务的响应返回给客户端之前" |
| **fallback** | 服务名称、服务协议、服务端口 | 官方示例：服务名称 `webmvc-mcp-server`、服务协议 `HTTP`、服务端口 `80` | 🔴 两条硬限制（原文）："**当路由发布时指向的后端服务为 FC 函数（函数计算）时，当前版本的 fallback 策略将会失效。**"；"**请注意，目前仅支持 HTTP 服务之间的 Fallback 能力。**" 触发条件："当路由指向的后端服务**没有可用节点**时，原请求会访问此处指定的 Fallback 服务" 定位："用于在请求的后端服务不可用时（如无可用节点），将请求引导至一个预设的备选服务或返回指定内容" |

**定位**："AI 网关支持对Agent API进行添加策略和配置插件，提高API的**安全性、性能和可维护性**。"

**🔴 重试策略（仅 Agent API 页有，参数完整）**

- **定位**："AI 网关提供API级别的重试设置，可以对出错的请求进行**自动重试**。根据需求配置重试条件，例如在连接失败、后端服务不可用，或者接收到指定的HTTP状态码时触发请求重试。"
- **总原则（官方"API的重试条件"原文）**："当后端服务返回`5xx`错误时，AI 网关按照设置的重试次数对出错的请求自动进行重试。"

| 参数 | 取值范围 / 默认值（逐字） | 说明 |
|---|---|---|
| **开启** | — | 🔴 **"关闭重试后，网关内部有默认重试配置，重试次数默认为2次，重试条件默认为 `connect-failure`、 `refused-stream`、 `unavailable`、 `cancelled`、 `non_idempotent`和 `retriable-status-codes`。"** → **关掉重试开关 ≠ 不重试** |
| **重试次数** | **"重试次数支持设置0\~10次，建议不超过2次。"** | **"重试次数设置为0，表示取消重试。"** |
| **重试条件** | "选择合适的，**支持多选**。" | 见下方两张条件表 |
| **重试状态码** | "对特定HTTP状态码的响应进行重试，**支持配置多种HTTP状态码**。" | 🔴 官方"重要"：**"**重试条件**指定`retriable-status-codes`，才能配置**重试状态码**。"** |

**HTTP 协议的重试条件**

| 条件 | 官方触发定义 |
|---|---|
| `5xx` | "如果后端服务返回任何`5xx`响应，或者发生连接断开、重置、读取超时事件，AI 网关将尝试对出错请求进行重试。" 官方"说明"：**"`5xx`包含`connect-failure`和`refused-stream`的条件。"** |
| `reset` | "如果发生连接断开、重置、读取超时事件，AI 网关将尝试对出错请求进行重试。" |
| `connect-failure` | "如果请求是由连接断开导致的出错，AI 网关将尝试对出错请求进行重试。" |
| `refused-stream` | "如果后端服务以`REFUSED_STREAM`错误代码来重置流，AI 网关将尝试对出错请求进行重试。" |
| `retriable-status-codes` | "如果后端服务响应结果的HTTP状态码匹配上指定的重试状态码，AI 网关将尝试对该请求进行重试。" 官方"说明"："**只有在重试条件中指定了`retriable-status-codes`，才能使用重试状态码。**" |

**gRPC 协议的重试条件**（官方表述统一为"如果后端gRPC服务的响应头部中的gRPC状态码为 X，AI 网关将尝试对该请求进行重试"）：`cancelled`、`deadline-exceeded`、`internal`、`resource-exhausted`、`unavailable`。

官方"说明"："重试策略配置完成且开启后，请根据实际业务**验证**服务重试规则是否生效。"

> 🔴 **SA 避坑（推理链见下）**：默认关闭态下网关仍会重试 **2 次**，且默认条件含 **`non_idempotent`**（非幂等请求也重试）。Agent 场景常有创建类动作（下单、发消息、写库），客户若后端非幂等，**必须显式把重试次数设为 0**（"重试次数设置为0，表示取消重试"），否则可能重复执行。
> [推断] 推理链＝官方「关闭重试后…重试次数默认为2次…重试条件默认为…`non_idempotent`…」+「重试次数设置为0，表示取消重试」两句直接组合，未添加外部信息。

**插件配置**：与 MCP 页流程一致（**添加插件** 页签 → **快捷导航** 选类型或搜名称 → 单击卡片 → 未安装则**安装并配置**／已安装则直接配置规则并选启用状态 → **确定**），差异仅在结尾："单击**确定**，返回**更多策略与插件**，可以查看API的插件挂载情况和启用状态。"（无拓扑图描述）

- 🔴 **删除的连带影响（官方原文，SA 必读）**："删除 Agent 会**解除该 Agent 与相关资源之间的关系，并移除相关授权**，但**不会删除**关联的 Agent API、Model API、服务、域名、消费者或消费者组。如不再使用这些资源，请前往对应资源页面**单独处理**。"

#### 8.16.4 配置 Agent 访问（入站）

支持类型："**百炼、Dify 和自定义**类型支持该能力。" 配置前"请准备可访问的 Agent 后端服务"。步骤：
1. 入口：创建 Agent 时展开 **Agent 访问能力配置（选填）**，或创建后在 **Agent 拓扑图** 页签的 **Agent 访问** 区域配置。
2. "选择已有域名，或单击 **添加域名** 创建域名。设置**访问路径**，将 Agent API 路由到对应的 Agent 后端服务。"
3. "如需校验调用方身份，在 **消费者认证** 卡片开启认证，并为**消费者或消费者组**授权。"
4. "如需对请求进行治理，在 **策略与插件** 卡片添加所需策略或插件。"
5. "确认 Agent API、消费者认证以及策略和插件的配置无误。"

结果："配置完成后，调用方可通过 **Agent API 的域名和访问路径**访问 Agent。"

🔴 **拓扑图的职责边界（官方"说明"原文）**："Agent 拓扑图**展示** Agent 与相关资源之间的关系。Agent API、服务、路由、域名和消费者**仍需在各自的资源页面管理**；这些资源发生变更后，拓扑图会同步更新。" → **拓扑图是视图，不是管理入口**。

#### 8.16.5 配置模型访问（出站）

支持类型："**Dify、Claude Code、DeepSeek Harness、Codex 和自定义**类型支持该能力。" 步骤：
1. 入口：创建 Agent 时展开 **模型访问能力配置（选填）**，或创建后在 **Agent 拓扑图** 页签的 **模型访问** 区域配置。
2. "选择已有 **Model API**，并确认**模型协议、BasePath 和域名**。如果没有可用的 Model API，可以通过页面入口创建。🔴 **Agent 客户端需要使用此处显示的接入点和 BasePath 访问模型**。"
3. 🔴 **消费者绑定（三条硬规则，官方原文）**："在 **消费者绑定** 卡片绑定**一个或多个**消费者。**同一个 Model API 可以关联多个 Agent，但在同一个 Model API 下，同一个消费者只能绑定到一个 Agent**，AI 网关根据这一绑定关系将模型调用统计到对应 Agent。如果没有可用的消费者，可以单击**创建消费者**。**绑定前，请确保消费者已获得所选 Model API 的访问权限；在此处绑定消费者不会自动为其授权。**"
4. "如需记录模型请求或进行内容安全防护，在 **策略与插件** 卡片开启或添加相应策略，例如 **AI 请求日志**、**AI 安全防护**。"
5. "确认 Model API、消费者绑定以及策略和插件的配置无误。"

> 🔴 **SA 避坑（两条）**：
> ① **消费者 ↔ Agent 在同一 Model API 下是 1:1 绑定**（跨 Model API 不受此限）。这既是限制也是**归因机制**——网关就是靠这个绑定关系把模型调用算到具体 Agent 头上。[推断] 由「AI 网关根据这一绑定关系将模型调用统计到对应 Agent」+「同一个 Model API 下，同一个消费者只能绑定到一个 Agent」推出：若两个 Agent 想共用一个消费者身份，则**无法在该 Model API 下分别统计**，必须为每个 Agent 分配独立消费者。
> ② **绑定不自动授权**。必须先在 Model API 侧给消费者授权，再来绑定；顺序颠倒会出现"绑定成功但调用被拒"。
> **AI 请求日志 / AI 安全防护** 的配置细节 → 归 W7（§10）/ W4（§7）。

#### 8.16.6 Agent 接入（把客户端流量引到网关）

**定位（官方原文）**："配置模型访问后，需要将**实际运行的 Agent 客户端改为通过 AI 网关调用模型**。接入后，Agent 的模型请求会经过 AI 网关，可以使用消费者认证、策略与插件，并查看 Agent 统计和会话用量统计。"

**获取接入信息**：Agent 管理 → 单击目标 Agent 名称 → **Agent 拓扑图** 页签 → 单击 Agent 卡片的 **Agent 接入** → "在接入指引选择 **API 协议**和**接入点**，并填写**访问模型、模型显示名称**及**用于鉴权的消费者**"。页面生成 4 项信息：

| 生成项 | 官方描述 |
|---|---|
| **API 地址** | "由**接入点**和 **Model API BasePath** 组成的 API 地址" |
| **协议** | "Model API 使用的协议" |
| **API Key** | "所选消费者的 API Key" |
| **模型名** | "Agent 客户端需要使用的**模型名称**和**显示名称**" |

**配置客户端**："控制台会**根据 Agent 类型生成接入步骤**，具体配置**以页面生成的接入指引为准**。"
以 **DeepSeek Harness** 为例，官方给出两种方式：
- **平台手动配置**："进入 DeepSeek Harness 的 **设置** \> **模型** \> **添加自定义提供方**，按接入指引填写 **Provider ID、显示名称、API 地址、API 协议和 API Key**，然后添加模型。"
- **本地配置文件**："按照接入指引合并 `~/.dsh/settings.yaml`，并设置所需环境变量。"
- **其他类型兜底**："对于其他 Agent 类型，按照控制台生成的接入指引操作。**如果客户端未提供专用指引，可使用其自定义端点或自定义模型提供方配置**，填写 AI 网关生成的 API 地址、协议、消费者 API Key 和模型名称。"

**🔴 验证与两个数据延迟（官方"重要"级原文，客户最常误判为"没生效"）**：
> "完成配置后，在 Agent 客户端发起一次模型调用。如果模型正常返回响应，并且可以在 AI 网关查到这次调用，说明接入成功。在观测页面查证调用记录时，请注意：**会话用量统计需要先开启会话分析，且只分析开启后新产生的调用，当日会话大盘约有 5 分钟的数据延迟**；**模型访问统计需要订阅每日分析，系统按日生成分析结果**。"

🔴 **凭证安全（官方"重要"原文）**："消费者 API Key 属于访问凭证，**请勿写入代码仓库或公开文档，建议通过客户端的凭据管理或环境变量保存。**"

#### 8.16.7 Agent 观测之一：会话用量统计

- **位置与门槛（官方原文）**："**会话用量统计** 位于 **FinOps** 下，🔴 **仅展示已配置模型访问的 Agent**。该功能将模型请求按会话和轮次整理，帮助找到用量较高或耗时较长的会话，并进一步定位出现异常的模型调用。"
- **数据层级（三层，逐字）**：

| 层级 | 官方定义 |
|---|---|
| **会话（Session）** | "用户与 Agent 的一次完整对话，可包含一个或多个轮次。" |
| **轮次（Turn）** | "用户的一次提问及 Agent 完成该问题的处理过程，🔴 **一个轮次可能因工具调用、重试等产生多次模型调用**。" |
| **模型调用** | "轮次内实际发起的一次模型请求，可查看模型名称、输入输出类型、结束原因、**首 Token 延迟（TTFT）**、Token 和耗时等信息。" |

- **开启会话分析**：目标实例左侧导航 → **FinOps** \> **会话用量统计** → "如果页面提示尚未开启，按照页面说明开启会话分析。**会话分析需要使用网关访问日志：如果已开启标准访问日志投递，系统会直接使用现有配置；如果尚未开启，页面会引导完成配置。**"
- 🔴 **只分析新数据（官方原文）**："开启会话分析后，**只分析新产生的调用，不会补充开启前的历史会话。**"
- 🔴 **连带计费（官方"说明"原文）**："**AI 网关不单独收取日志费用，日志服务 SLS 会根据实际使用量计费**，具体计费方式请参见开启网关日志投递。" → SA 报价时必须把 SLS 用量算进全成本（口径归 W2 §3 / W7 §10）。

**会话大盘的 4 个分析区域**

| 分析区域 | 官方说明 |
|---|---|
| **概览** | "所选 Agent **当日**的会话数和消费者数。" |
| **会话性能与资源消耗分布** | "会话 Token、会话耗时和会话 Credits 的 **P50、P90**。" |
| **Session 排行** | "分别按 **Token、总耗时和 Credits** 展示用量较高的会话。" |
