## S1：电商大促弹性架构

> **证据等级**：[官方] help.aliyun.com + [实战] 双11 公开数据
> **匹配模板**：architecture-templates.md T2

### 场景特征

- 常态 QPS 1K-10K，大促峰值 10X-100X
- 库存一致性要求高（超卖 = 资损）
- 成本敏感：峰值只持续 4-8 小时，其余时间资源闲置
- 弹性窗口：需要 5 分钟内完成 10 倍扩容

### 核心产品组合

```
用户 → DCDN(动静加速) → WAF(CC+Bot防护) → ALB(HTTP/2, 灰度)
        │
  ┌─────┴─────┐
  │           │
ACK Pro      ECI/ACS(弹性层)
(核心微服务)  (突增流量吸收)
  │           │
  └─────┬─────┘
        │
  ┌─────┼─────────────┐
  │     │             │
PolarDB-X  Tair       RocketMQ        OSS
(订单/商品) (热点缓存)  (削峰填谷)    (图片/文档)
                         │
                   异步 → Hologres(实时分析) + MaxCompute(离线)
```

### 关键决策点

| 决策 | 选项 A | 选项 B | 触发条件 |
| --- | --- | --- | --- |
| 计算弹性 | ACK + ECI 抢占 | ACS 全 Serverless | 峰谷比 >5x 且无 Ops 团队 → ACS |
| 数据库 | PolarDB（单写多读） | PolarDB-X（分布式） | 单表 >5 亿行 或 写 TPS >10 万 → PolarDB-X |
| 缓存热点 | Tair 集群版 | Tair 读写分离 | 单 Key QPS >10 万 → 热 Key 打散 |
| 库存扣减 | Tair 原子扣减 + DB 异步落 | Seata 分布式事务 | 多品类联合库存 → Seata |
| 流量削峰 | RocketMQ + 异步消费 | Sentinel 限流直接拒绝 | 下游能追平 → MQ；否则 → 限流 |

### 弹性策略三层模型 [官方]

| 层级 | 策略 | 扩容时间 | 成本 |
| --- | --- | --- | --- |
| 基础层 | ECS/ACK 固定节点 + RI/包年 | N/A（常驻） | 最低单价 |
| 弹性层 | ECI 抢占式 + HPA | ~30 秒 Pod 就绪 | 按秒计费，抢占最低 1 折 |
| 极端层 | ACS Serverless + FC | ~10 秒 | 按调用计费 |

### BOM 估算（10 万 QPS 峰值，4 小时大促）[推断]

| 组件 | 规格 | 月均成本(CNY) | 大促追加 |
| --- | --- | --- | --- |
| ALB | 性能保障型 | ~2,000 | 0（按 CU 自动） |
| ACK Pro 管控面 | Pro M | ~460 | 0 |
| 常驻 ECS | ecs.g7.2xlarge × 10 | ~15,000 | 0 |
| ECI 弹性 | 4C8G × 100 Pod × 4h | 0 | ~2,000/次 |
| PolarDB-X | 4 节点 8C32G | ~12,000 | 只读扩容 |
| Tair | 集群版 64G | ~6,000 | 0 |
| RocketMQ | Professional 实例 | ~3,000 | 0 |
| **合计** | | **~38,000/月** | **+2,000/次大促** |

### 客户案例参考

- **bilibili 游戏**：ECS + RDS + PolarDB + DTS + SLB + CDN，大促弹性扩缩容 + 防 11 起风险 [官方]

### 踩坑清单 [实战+推断]

1. ECI 抢占实例可能被回收 — 必须配合 ACK 中断处理 Hook + 优雅下线
2. Tair 大 Key 超时 — 提前做 Key 拆分（单 Value < 10KB 原则）
3. RocketMQ 积压 — 消费者数必须 >= 队列数，否则堆积
4. PolarDB-X DDL — 分布式 DDL 慢，大促前至少 48h 完成变更
5. WAF CC 防护阈值 — 大促前临时上调白名单，否则把真用户拦住

## S2：游戏出海 / 跨境游戏服务端

> **证据等级**：[官方] + [实战] bilibili/鹰角/KLab + [推断] 延迟模型
> **匹配模板**：architecture-templates.md T4（出海双活）

### 场景特征

- DAU 10 万 - 100 万级，全球多 Region 部署
- 实时 PvP 对延迟极敏感（<100ms 可玩，<50ms 优秀）
- 游戏逻辑服有状态（房间/匹配/战斗）
- 合规：不同地区数据驻留 + 支付牌照 + 内容审核
- 反作弊：外挂检测 + 安全通信

### 核心产品组合

```
全球玩家
   │
   ├─ 东南亚 → 新加坡 Region
   ├─ 中东 → 迪拜 Region (ae-dubai-1)
   ├─ 北美 → 美东 Virginia
   └─ 中国 → 杭州/上海 Region
         │
   ┌─────┴─────┐
   │           │
  GA(全球加速)  DCDN(静态资源)
   │
  ALB + WAF(DDoS高防)
   │
  ┌──────────────────────────┐
  │ ACK/ECS 集群              │
  │ ├─ 网关服(无状态)          │
  │ ├─ 匹配服(Redis队列)      │
  │ ├─ 房间服(有状态, ECS独占) │
  │ └─ 战斗服(有状态, UDP)     │
  └──────────────────────────┘
         │
   ┌─────┼──────────┐
   │     │          │
 Tair   PolarDB   OSS(热更包)
(排行/匹配) (账号/道具)
         │
       DTS(跨Region同步)
```

### 游戏特有架构模式

**1. 匹配服务（Matchmaking）**
```
玩家请求 → API 网关 → 匹配队列(Tair List) → 匹配算法(ELO/Glicko)
         → 找到对手 → 分配房间 → 通知双方房间服 IP:Port
```
- Tair 做匹配池（ZSet 按分数段索引），匹配延迟 < 5s
- 跨 Region 匹配：优先本地，等待超时后扩大到邻近 Region

**2. 房间/战斗服（Stateful Game Server）**
- 每个 ECS 独占运行 N 个房间进程
- UDP 通信（KCP 可靠传输协议）
- 状态不落库（战斗结束后一次性写入结算）
- 使用 ESS + 自定义指标（房间数/CPU）弹性伸缩

**3. 反作弊**
- 客户端校验 + 服务端权威判定（War Authoritative Server）
- 行为分析：异常操作频率、移动速度超限 → 标记 + 举报
- 阿里云 WAF Bot 防护 + 自建规则引擎

| --- | --- | --- | --- |
| 解析 | 百炼文档理解 API（支持 OCR+表格+版式） | 10万×50页=500万页 | 按页计费 ~¥50,000 一次性 |
| 分块 | 语义分块（推荐 512-1024 token/chunk） | 10万文档 → ~500-1000万 chunks | — |
| Embedding | text-embedding-v4 (1024维) | 500-1000万 chunks | ~¥5,000 一次性 |
| 存储 | 百炼旗舰版 or Hologres 向量 | ~50-100GB 向量数据 | 旗舰版 ~¥1,500/月(10RCU) |
| 检索 | 混合检索(BM25+向量) + Reranker | 50-500 QPS | RCU 按需扩展 |
| 增量更新 | 文档变更触发重新 embedding | 每日~100份增量 | 忽略不计 |

**分块策略最佳实践**：
- 语义分块优于固定长度（保留段落/章节完整性）
- 推荐 chunk size：512-1024 token（过短丢上下文，过长检索噪音多）
- 重叠（overlap）：50-100 token
- 表格/图片：单独作为 chunk，附带上下文描述
- 层次化索引：章节级摘要 + 段落级详情（Parent-Child 结构）

**向量库选型（10万文档级）**：

| 向量库 | 适合规模 | QPS | 特点 | 月成本量级 |
| --- | --- | --- | --- | --- |
| 百炼内置知识库（旗舰） | ≤9999GB | ≤10000 QPS | 全托管零运维 | 1,500-15,000 |
| Hologres 向量 | TB 级 | 万级 | OLAP+向量混合查询 | 3,500+ |
| Lindorm 向量 | PB 级 | 万级 | 低成本大容量 | 1,000+ |
| OpenSearch 向量 | 中等 | 万级 | 全文+向量混合 | 2,000+ |
| DashVector | 中小 | 千级 | 全托管 Serverless | 500+ |

### 数据库灾备快速决策树（Mode F 速查表）[官方+推断]

> 用于 30 秒内快速给出灾备方向性判断。

**PolarDB MySQL 灾备关键数据**：
- 三可用区部署（存储热备集群）：RPO=0（X-Paxos 强同步），SLA 99.995%
- 热备开启：主备切换 RTO 5-10 秒
- 未开热备：主备切换 RTO 20-30 秒，极端不超 3 分钟
- 跨可用区自动切换：RPO <100ms（异步模式），RTO <30 秒
- 存储热备集群模式：RPO=0（同步模式），RTO <60 秒
- 最大支持数据量：100TB（企业版 200TB）
- GDN 跨 Region 复制延迟：<2 秒

**RDS MySQL（已停止新购三节点企业版，推荐迁移到 PolarDB）**：
- 高可用版（双机热备）：RPO <1 分钟（半同步），RTO 1-5 分钟
- 注意：三节点企业系列 2023年3月已停止新购

**MySQL → PolarDB 迁移**：
- DTS 支持全量+增量迁移，兼容性 99.9%
- 大表迁移吞吐：10+MB/s（取决于网络和实例规格）
- 支持 MySQL 5.6/5.7/8.0 → PolarDB MySQL
- 一键升级入口：RDS 控制台直接升级到 PolarDB

**决策树**：
```
输入：{DB类型, 数据量, TPS, 目标RPO, 目标RTO}

IF MySQL/PG 且 RPO=0 且 RTO<30s:
  → PolarDB 三可用区 + 存储热备 + 热备开启
  → 安全区：数据量<100TB, 写TPS<10万
  → RTO 实测：5-10秒（热备）
  → 成本增量：~40-50%（额外只读节点 + 跨AZ存储副本）
  → 迁移路径：DTS 全量+增量迁移

IF MySQL/PG 且 RPO=0 且 RTO<60s:
  → PolarDB 三可用区 + 存储热备集群
  → X-Paxos 强同步保证 RPO=0
  → 成本增量：~30-40%

IF MySQL/PG 且 RPO<1min 且 RTO<5min:
  → PolarDB 多AZ 高可用版（无存储热备）
  → 或 RDS 高可用版跨AZ
  → 成本增量：~15-20%

IF RPO=0 且 需要异地灾备:
  → PolarDB-X 两地三中心（5副本 Paxos）
  → 同城 RPO=0, RTO<30s；异地 RPO=分钟, RTO<30min
  → 适合金融监管要求
  → 成本增量：80-100%

IF Oracle 且需国产化:
  → OceanBase（三副本 Paxos，RPO=0，RTO <30s）
  → 兼容 Oracle 语法（MySQL+Oracle 双模式）
```

**成本估算（8C32G PolarDB，单AZ → 跨AZ RPO=0）** [推断]：

| 配置 | 月成本(CNY) | 增量 |
| --- | --- | --- |
| 单AZ 基础版 | ~4,500 | 基线 |
| 多AZ 高可用（半同步） | ~5,800 | +29% |
| 三可用区存储热备（RPO=0） | ~6,800 | +51% |
| +GDN 异地从集群 | ~10,000 | +122% |

**30 秒应答模板**：
> "可以做到。方案是 PolarDB MySQL 三可用区部署 + 存储热备 + 开启热备节点。8TB 在安全范围内（上限 100TB），TPS 5000 远低于阈值。RPO=0 由 X-Paxos 强同步保证，RTO 5-10 秒（开启热备时）。成本比单AZ增加约 50%。迁移路径：DTS 从 MySQL 一键迁移，兼容性 99.9%。"

                   ┌─────── 点播链路 ───────┐

| 高清点播 | 1280×720 | 2.0Mbps | 1.2Mbps | 30fps |
| 超清点播 | 1920×1080 | 4.0Mbps | 2.5Mbps | 30fps |

### 踩坑清单 [实战+推断]

1. **转码费暴涨** — 每个视频默认转 6 路码率 = 6 倍计费，需按用户设备分布裁剪模板(80% 手机只需 720P+1080P)
2. **CDN 回源比过高** — 热门视频预热 + 分层缓存(L1+L2)，目标回源比 <5%
3. **直播卡顿排查** — 70% 卡顿发生在"最后一公里"(用户侧)，需端上埋点 + SLS 分析区分推流/CDN/播放端问题
4. **H.265 兼容性** — iOS Safari 原生支持，部分 Android WebView 不支持 → 需备 H.264 兜底流
5. **弹幕洪峰** — 单房间 10 万+弹幕/秒时 Tair 单 Key 瓶颈 → 按房间分片 + 客户端合并渲染(50ms 批次)
6. **DRM 密钥泄露** — 定期轮换 Key，配合防录屏水印(用户 ID 隐形水印)追溯泄露源
7. **OSS 生命周期** — 原始视频转码完成后 7 天转 IA，180 天转归档，节省 60% 存储费

### 踩坑清单 [实战+推断]

1. **千万级长连接分集群** — 单 IoT 实例 200 万连接上限，需提前规划分集群策略(按地域/设备类型)，灰度迁移
2. **MQTT QoS 选择** — QoS 0 丢消息(位置上报可接受)；QoS 1 至少一次(命令下发必须)；QoS 2 开销大(仅关键控制用)
3. **时序数据 TTL 未设计** — Lindorm 不设 TTL 会无限膨胀，7 天热 → 90 天降采样 → 归档到 OSS，节省 70% 存储

5. **Kafka 分区数不够** — 5000 万 TPS 需要 500+ 分区(每分区 10 万 TPS)，创建后不可缩减，提前规划
6. **OTA 灰度不充分** — 5000 万台全量推送 = 灾难，必须 1%→5%→20%→100% 逐步灰度 + 异常自动回滚
7. **围栏计算性能** — 5000 万设备 × 实时围栏判断 → 不能逐条查 DB，需 Tair 缓存围栏多边形 + 本地计算(R-Tree 索引)

| 会员 ID 打通 | 手机号为主键 | ID-Mapping 图(手机+设备+OpenID) | 多渠道账号体系不统一 → ID-Mapping 图 |

### 会员 ID-Mapping 设计 [推断]

```
手机号(主键)
    │
    ├── 微信 OpenID_1 (小程序)
    ├── 微信 OpenID_2 (公众号)
    ├── 支付宝 UID
    ├── 天猫 nick
    ├── 门店会员卡号(旧系统)
    └── 设备指纹(App IDFA/OAID)

Hologres ID-Mapping 表设计：
- one_id (bigint, 主键)
- id_type (enum: phone/wechat/alipay/tmall/card/device)
- id_value (varchar)
- bindTime / confidence_score
```

> 核心逻辑：以手机号为锚点，通过注册/登录/支付行为绑定其他 ID，置信度衰减机制。

### 踩坑清单 [实战+推断]

1. **门店网络质量差** — 部分商场 WiFi 丢包率 >5%，POS 数据需本地 SQLite 缓存 + 断点续传，不能依赖实时上传
2. **POS 数据格式不统一** — 2000 店可能有 3-5 种 POS 系统(百胜/海鼎/科脉)，需建 ETL 适配层(DataWorks 数据集成 + 自定义 Reader)
3. **会员去重逻辑复杂** — 同一人多手机号/多店注册 → ID-Mapping 需置信度机制 + 人工审核队列
4. **实时库存不准** — POS 离线时本地扣库存，上线后与中心冲突 → 需要冲突合并策略(以 POS 实际为准+差异告警)
5. **大促数据洪峰** — 双11 交易量 10 倍于平日，Flink 需提前扩容 + Kafka 预留 Partition，否则消费积压
6. **会员隐私合规** — 《个人信息保护法》要求：收集需明示同意、跨平台共享需单独授权、退会需删除 → 技术上需数据打标+删除链路
7. **Quick BI 报表慢** — 2000 店 × 365 天 × 10 万 SKU = 百亿行明细，直接查 Hologres 需预聚合(DWS 层)，否则超时

## S9：SaaS 多租户架构

> **证据等级**：[官方] help.aliyun.com ACK/PolarDB/MSE 文档 + [推断] 成本+架构模型
> **匹配模板**：architecture-templates.md T2

### 场景特征

- SaaS ISV，500+ 企业客户(租户)，日活 3 万用户
- 从 IDC 自建迁移到阿里云，需要平滑过渡
- 多租户隔离：数据安全 + 性能互不影响 + 按租户计费
- 弹性需求：工作日白天峰值，夜间/周末低谷(峰谷比 3-5x)
- 大客户定制：部分 VIP 租户需要独立资源 + 定制功能

### 核心产品组合

```
                   SaaS 用户(浏览器/App)
                          │
                     ALB(7 层负载均衡)
                     (按租户域名/Header路由)
                          │
                   ┌──────┴──────────────────────────┐
                   │  ACK Pro 集群                      │
                   │                                   │
                   │  ┌─ Namespace: shared ──────────┐ │
                   │  │  微服务 A/B/C (通用租户)      │ │
                   │  │  Sidecar: MSE Envoy(限流)    │ │
                   │  └──────────────────────────────┘ │
                   │                                   │
                   │  ┌─ Namespace: vip-tenant-X ───┐ │
                   │  │  微服务 A/B/C (VIP 独享)     │ │
                   │  │  独立资源配额(ResourceQuota) │ │
                   │  └──────────────────────────────┘ │
                   └──────┬──────────────────────────┘
                          │
            ┌─────────────┼─────────────────┐
            │             │                 │
     PolarDB Serverless  Tair           RocketMQ
     (多租户数据库)    (会话缓存+     (异步任务队列)
            │          租户配置)
            │
      ┌─────┴─────┐
      │           │
  shared-DB    isolated-DB
 (tenant_id列)  (VIP独立库)
            │
     ┌──────┴──────┐
     │             │
   MSE Nacos    MSE Sentinel        ARMS + SLS
  (服务注册+    (租户级限流)       (可观测+审计)
   配置中心)
```

### 多租户数据库隔离模型 [推断]

| 模式 | 适用 | 隔离度 | 成本 | 运维复杂度 |
| --- | --- | --- | --- | --- |
| Shared-DB + tenant_id 列 | 标准租户(<100 用户) | 低(应用层隔离) | 最低 | 低 |
| Shared-Instance + Schema/DB 隔离 | 中型租户(100-1000 用户) | 中(DB 级权限) | 中 | 中 |
| Isolated-DB(独立 PolarDB 实例) | VIP 大客户(>1000 用户) | 高(物理隔离) | 高 | 高 |

**推荐混合策略**：
```
500 个租户分布：
├── 450 个标准租户 → 1 套 PolarDB Serverless (shared-DB, tenant_id 列)
├── 40 个中型租户 → 1 套 PolarDB (多 Schema 隔离)
└── 10 个 VIP 大客户 → 各自独立 PolarDB 实例
```

### 关键决策点

| 决策 | 选项 A | 选项 B | 触发条件 |
| --- | --- | --- | --- |
| DB 隔离模式 | Shared-DB(tenant_id) | Isolated-DB(独立实例) | VIP/合规要求物理隔离 → Isolated；通用 → Shared |
| 计算隔离 | 共享 Deployment(所有租户) | VIP 独立 Namespace | 大客户 SLA 99.99% → 独立 Namespace + ResourceQuota |
| 弹性策略 | PolarDB Serverless(自动伸缩) | PolarDB 固定规格 | 峰谷比 >3x → Serverless；稳定负载 → 固定规格 |
| 租户限流 | MSE Sentinel(应用级) | ALB 限流(网关级) | 需按租户套餐精细限流 → MSE Sentinel |
| 租户路由 | 应用层(Header: X-Tenant-ID) | DNS 域名(tenant.saas.com) | VIP 需独立域名 → DNS；标准 → Header |
| 配置管理 | MSE Nacos(租户级配置) | 数据库配置表 | 需热更新+灰度 → Nacos；简单开关 → DB |

### 租户级限流设计(MSE Sentinel) [官方+推断]

```
限流维度：
├── 全局限流：整体 QPS 上限保护后端(如 10 万 QPS)
├── 租户级限流：
│   ├── 免费版：100 QPS / 租户
│   ├── 专业版：1000 QPS / 租户
│   └── 旗舰版：5000 QPS / 租户 + 独立资源
└── API 级限流：单个接口独立阈值

MSE Sentinel 规则配置：
- 资源名：{serviceName}:{tenantId}
- 阈值类型：QPS
- 流控效果：排队等待(平滑) / 直接拒绝(保护)
- 降级策略：慢调用比例 > 50% → 熔断 5s
```

### IDC → 阿里云迁移方法论 [推断]

| 阶段 | 内容 | 周期 | 风险 |
| --- | --- | --- | --- |
| Phase 1：评估 | 应用依赖梳理 + 云资源评估 + 迁移方案 | 2-4 周 | 低 |
| Phase 2：试点 | 选 1-2 个小租户迁移，验证全链路 | 4-6 周 | 中(可回滚) |
| Phase 3：批量迁移 | DTS 数据同步 + 灰度切流(10%→50%→100%) | 6-8 周 | 中 |
| Phase 4：优化 | 利用云原生能力优化(Serverless/弹性/可观测) | 持续 | 低 |

**迁移关键工具**：
- **DTS**：数据库在线迁移(全量+增量)，零停机切换
- **SMC**：服务器整机迁移(IDC VM → ECS)
- **ADAM**：应用架构评估 + 改造建议

### PolarDB Serverless 弹性表现 [官方]

| 指标 | 数值 |
| --- | --- |
| 最小规格 | 0 PCU (暂停时不收费) |
| 最大规格 | 32 PCU (自动扩展) |
| 扩容速度 | 秒级(1 PCU ≈ 1C2G) |
| 缩容延迟 | 5 分钟无负载后自动缩回 |
| 适用场景 | SaaS 多租户(白天高/夜间低)、开发测试 |

> 1 PCU ≈ 0.28 CNY/hr，夜间缩至 2PCU、白天峰值 16PCU → 月均成本仅为固定 8C32G 的 40-50%。

### 踩坑清单 [实战+推断]

1. **Noisy Neighbor(吵闹邻居)** — 某租户大查询拖垮共享 DB → PolarDB 资源组(Resource Group)隔离 CPU/IO + Sentinel 限流双保险
2. **大租户数据量倾斜** — 10 个 VIP 占 80% 数据量，shared-DB 索引膨胀 → 提前拆分到独立库(数据量 >50GB 触发迁移)
3. **升级兼容性** — 500 租户不可能同时升级，需要灰度发布(Namespace 级) + Feature Flag + 多版本 API 共存(至少 N-1)
4. **租户级数据备份恢复** — PolarDB 全量备份无法单租户恢复 → 需要应用层逻辑备份(mysqldump per tenant) + PITR(时间点恢复)
5. **连接池耗尽** — 500 租户 × 微服务池 = 连接数暴涨 → PolarDB Proxy 连接池复用(server-side pooling)，或 ProxySQL
6. **MSE 限流规则爆炸** — 500 租户 × 20 接口 = 1 万条规则 → 按套餐模板批量生成，而非逐条配置
7. **迁移割接夜** — DTS 增量同步延迟 >0 时切换 = 数据丢失 → 需等待增量追平(延迟 <1s) + 短暂停写(30s) + 验证 → 切换 DNS
8. **租户数据删除** — 退租后需彻底清除(PIPL 合规)，shared-DB 需 DELETE WHERE tenant_id=X + 二次确认 + 审计日志
