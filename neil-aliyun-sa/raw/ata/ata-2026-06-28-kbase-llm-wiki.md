Karpathy 在 2026 年初提出了 LLM Wiki 方法论（原文），核心思想是让 LLM 不再每次从原始文档中检索，而是增量构建和维护一份结构化的 Wiki。他说这套东西“仍然像一堆 hacky scripts，但有空间做成 incredible new product”。我们在 KBase 上尝试走通了这条路——远端知识库 + 本地客户端 + CLI 工具链，本文记录这条路径的实践。 前言：一个知识管理的结构性问题 Kbase 作为阿里内部知识管理平台，接入了钉钉文档、语雀文档、代码仓库 Wiki、OSS 采集等多种数据源。长期以来，系统对这些文档的处理方式是标准的 RAG 模式：切片 → 向量化 → 检索 → 拼凑回答。 RAG 模式在检索准确性上已经做得很好，但它有两个结构性的局限——召回不精准和知识不积累： 同一个概念往往分散在多篇文档中，语义相似但上下文不同。用户问“认证模块怎么设计的”，召回的可能是权限、登录、OAuth、SSO 等多篇文档的混杂片段——语义都和“认证”相关，但不是用户真正想要的答案 即使召回了正确的片段，LLM 也是每次都从零开始重新拼凑。问十次，做十次同样的拼凑，答案不会越来越好 知识库里有 50 篇钉钉文档、30 篇语雀文档，内容之间有重叠、有矛盾、有关联，但用户看到的只是一个文档列表 Karpathy 在 2026 年初提出了一种新的范式：不要在查询时从原始文档检索，而是让 LLM 增量构建和维护一份持久化的 Wiki——一组结构化的、相互链接的 markdown 文件。知识被编译一次然后持续更新，而不是每次查询时重新推导。 我们在两个方向上落地了这个理念：远端 KBase 平台的 Wiki 层和本地 KBase Mind 客户端。本文记录这两条路径的工程实践。 一、核心概念：编译思维与三层架构 先明确 LLM Wiki 的几个核心概念。 编译 vs 检索 维度 RAG（检索模式） LLM Wiki（编译模式） 知识组装时机 查询时临时拼凑 提前编译好，随时可用 状态性 无状态，每次从零推导 有状态，知识持续积累 文档处理 片段化切割，语义割裂 全文理解，重构知识网络 增量更新 追加入库，无知识关联 增量编译，自动更新交叉引用 一个形象的类比：RAG 像是每次都拆快递箱找东西的仓库，LLM Wiki 像是已经分类收纳好、贴好标签的柜子。 三层架构 所有 LLM Wiki 实现（无论远端还是本地）共享同一个分层模型： raw/（原始数据层）：AI 只读不写，是唯一的事实来源。你的文档、会议纪要、PPT、PDF 都放在这里 _wiki/（衍生知识层）：AI 编译产出的结构化知识库，包含全局索引、各主题页面、知识图谱 Schema（规范配置）：定义编译规则、查询规则、健康检查规则，是人和 AI 之间的契约 分层确保了三件事：原始数据永不丢失、知识可追溯可回滚、责任边界清晰（人管 raw，AI 管 wiki）。 三个核心操作 操作 触发条件 做什么 Ingest（摄入） 新文档进入 raw/ 生成/更新 Wiki 页面，建立交叉引用，更新索引 Query（查询） 用户提问 先读索引定位相关页面，综合回答，高价值 Q&A 可存回 Wiki Lint（健康检查） 定期或手动触发 检查矛盾、孤岛、过时、缺失的交叉引用 Skill：编译规则的载体 上述三层架构和三个操作的具体规则，都定义在一份 Skill 文件中。Skill 是人和 AI 之间的契约文档，它告诉 Agent：知识库的主题范围是什么、如何编译、如何查询、如何做健康检查。 我们提供了开箱即用的 KBase LLM Wiki Skill，你可以直接使用或基于它补充自己的编译规则Skill：kbase-llm-wiki 二、远端实践：KBase 平台的 Wiki 层 2.1 Wiki 层的核心设计 Wiki 就是知识库里的文档。Wiki 文章和用户的原始文档存在同一个知识库中，天然复用现有的版本管理和权限控制。用户看到的是一个统一的知识库，原始文档和 Wiki 文章共存。 关联关系写在内容里。每篇 Wiki 文章的开头记录了它引用了哪些原始文档、与哪些其他主题相关，这些关联信息直接嵌入在文章中，而不是散落在别处。基于这些关联关系，系统自动生成知识图谱，展示文档之间的关联网络（详见 QCon 案例中的图谱截图）。 Wiki 层默认不参与向量化检索。向量化检索由原始文档承担，Wiki 层专注于提供全局视图和知识导航。后续我们会为 Wiki 层提供单独的查询机制。 Wiki 查询内置于 Skill。KBase LLM Wiki 的 Skill 中已包含查询规则——Agent 回答问题时优先从 Wiki 中查找，必要时回溯原始文档，所有引用精确指向原始来源。 2.2 平台 Agent 集成：知识助手驱动 Wiki 生成 在 KBase 平台上，用户无需手动编写 Wiki——平台内置的知识助手可以直接驱动 Wiki 的生成和补充。实际使用中，左侧查看已编译的 Wiki 结果，右侧通过知识助手持续对话，补充和完善待生成的 Wiki 内容，形成「边看边补」的协作模式。 KBase 平台知识助手驱动 Wiki 生成截图——左侧为 Wiki 编译结果（log.md / 主题页面），右侧为知识助手对话面板，展示持续补充 Wiki 内容的场景： 2.3 实践案例：QCon 2026 分享文档的 Wiki 化 以 QCon 三、客户端实践：KBase Mind 远端 Wiki 层解决了团队级知识管理问题。但 Karpathy 的原始方法论更侧重个人场景——本地文件夹 + 编辑器 + Agent。我们在客户端方向做了第二条实践路径。 3.1 定位与差异 KBase Mind 是一个对标 Obsidian 的本地知识库客户端，核心差异化在于内置 Karpathy 编译流程、内置 Claude Code和与 KBase 平台的双向打通： 维度 Obsidian KBase Mind 存储 本地 Markdown 本地 Markdown + 三层结构（raw/wiki/索引） 链接 [[双向链接]] + 知识图谱 同，且 Wiki 层自动维护关联关系 Agent 集成 需安装社区插件 内置 Claude Code，配置 API Key 即可使用 同步 iCloud / Git / Obsidian Sync 与 KBase 双向同步 编译 无（纯笔记） 内置编译：raw → wiki → 索引 浏览器集成 无 KBase 浏览器插件集成 3.2 核心能力 内置 Claude Code：客户端直接集成 Claude Code，用户在本地即可完成知识编译、查询、整理等全流程操作，无需切换工具 与 KBase 双向同步：个人积累的内容可一键推送到团队知识库，团队知识也可拉取到本地 KBase 浏览器插件集成：在浏览器中随时将网页内容捕获到本地知识库。一个典型的工作流是：在网页端浏览时随手收藏有价值的文档和参考资料，这些内容自动进入本地 raw/ 层，然后结合已有的知识库内容，让 Agent 编译生成新的 Wiki 主题页或更新已有页面——从素材收集到知识编译一气呼成 多格式文档支持：支持 PPT、PDF 等非 Markdown 文档的直接渲染和预览，导入时自动转换为可编译格式 开放接入：客户端内置了对 Cursor、Claude Code、Windsurf、Qoder 等主流 AI 工具的支持，用户一键开启即可完成 MCP 配置和 Skill 注入，无需手动设置 3.3 与 a1 CLI 的集成 KBase 的 Wiki 操作已完整集成到 a1 kbase CLI 工具链中，实现与 KBase 平台的双向打通。详细命令参考见 a1 kbase 命令文档。 3.4 使用说明 Kbase Mind安装使用 四、快速上手与关键经验 4.1 在 KBase 平台上开始 KBase LLM Wiki 介绍 从「每次现查」到「越用越厚」：KBase 上的 LLM Wiki 实践 4.2 在 KBase Mind 客户端上开始 如果你已经有 KBase 知识库，最快的方式是直接从平台同步到本地： 打开 KBase Mind，登录 a1 选择要同步的知识库，一键拉取到本地 开启你常用的 AI 工具（如 Claude Code），开始编译 如果你还没有 KBase 知识库，也可以直接打开本地已有的任意文件夹作为知识库目录，配置好claude code apiKey（可使用百炼的anthropic端点）即可触发初始化三层结构（raw / _wiki ）； 4.3 Schema 是人和 AI 的契约 所有成功的 LLM Wiki 实践都有一个共同特征：Schema 驱动。 Schema 不是数据结构定义，而是知识库的“宪法”——它规定了知识库的主题范围、文件组织规则、编译规则、查询规则、健康检查规则。人定框架，AI 在框架内填充。 4.4 多对一映射是核心能力 LLM Wiki 最有价值的能力不是“1 篇文档生成 1 篇 Wiki”，而是多篇原始文档编译为同一篇主题页。这体现了从“情景记忆”到“语义记忆”的映射——5 篇关于认证的散落文档，编译为 1 篇《认证模块总览》，同时保留对每篇源文档的精确引用。这正是 QCon 案例中 72 篇文档编译为 14 个主题页的核心价值。 4.5 首次编译不必追求一步到位 当原始资料较多时，不要期望一次编译就生成完整的 Wiki——Agent 单次探索的范围有限，很容易遗漏部分文档。更好的做法是**分批引导、逐步完善**：先让 Agent 对一部分核心资料做首轮编译，检查结果后指出遗漏的方向，引导它补充。后续新增的文档只需做增量编译，Agent 会在已有 Wiki 结构上持续扩展，不必每次从头来过。 4.6 RAG 和 LLM Wiki 是互补关系 场景特征 推荐方案 海量文档、高并发 RAG 合规溯源、原文保真 RAG 个人知识管理、小团队 LLM Wiki 中等规模、需要深度理解 LLM Wiki 跨文档综合推理 LLM Wiki 海量文档 + 需要概念级理解 RAG 底座 + Wiki 上层 在 KBase 的实践中，原始文档负责细节级检索，Wiki 层负责结构化导航和全局视图。两者各司其职，互补而非替代。 五、未来方向 远端 KBase 平台 定时任务触发 Wiki 编译（使用Devix Cloud CLI定时管理LLM Wiki）。当前 Wiki 编译主要靠用户手动触发。下一步是实现事件驱动的自动编译：原始文档变更后自动触发增量编译，支持定时任务和事件回调，用户无需手动操作。 Wiki 层独立查询（已支持，LLM Wiki Query 使用文档）。目前 Wiki 层默认不参与向量化检索。我们计划为 Wiki 层提供单独的索引与查询机制，让用户可以直接通过 Wiki 数据进行查询——这是一条区别于传统 RAG 的新路径，从“检索原始片段”走向“查询结构化知识”。 本地 KBase Mind 客户端 知识库健康检查。引入知识健康度机制：定期扫描孤立页面、过期内容、断链、矛盾检测，生成健康报告和修复建议，确保知识库质量随时间可控。 定时任务与主动提醒。支持用户设置定时任务，如“每周一自动编译新增文档”、“每月进行一次健康检查”、“每天下班前提醒更新工作日志”，让知识库从被动工具变成主动的知识管理伙伴。 Git 版本管理。为知识库引入 Git 版本控制，文件保存时自动提交，用户可以查看任何文件的历史版本、对比变更、回滚到任意时点——知识库的版本管理和代码仓库一样可靠。 每日回顾与知识沉淀。自动分析当天的文件变更和知识积累情况，生成每日回顾报告，帮助用户反思知识增长趋势，把知识库从“存储工具”变成“认知成长伙伴”。 更多 AI 工具与模型支持。扩展 AI 工具接入能力，支持用户自定义注册 Agent；同时支持更多 LLM Provider，让用户可以自由选择适合自己的模型。 知识创作与文档生成 知识库不仅是知识的汇聚地，也应该是创作的起点。我们计划支持基于知识库内容快速生成周报、技术方案、分享文档等创作文档——积累的知识直接变成可交付的成果，而不是每次都从零开始写。 总结 Karpathy 说："这套东西目前仍然像一堆 hacky scripts，但有空间做成 incredible new product。" 我们在两个方向上验证了这个"incredible new product"的可行性： 远端 KBase Wiki 层：将 Karpathy 方法论集成到企业知识管理平台，QCon 72 篇文档编译为 14 个主题 Wiki，知识图谱一目了然 本地 KBase Mind 客户端：内置 Claude Code + KBase 双向同步 + 浏览器插件 + 多格式支持，任何 AI 工具都可接入编译流程 如果你是程序员，好消息是你不需要学任何新东西。代码仓库怎么管，知识库就怎么管。你积累了这么多年的工程直觉——分层、增量编译、CI/CD、代码审查——终于可以用在自己的笔记上了。 别让你的知识腐烂。让它们被编译。 目前我们已在远端和客户端两个方向开展了实践，但该方案仍有不少不完善之处，我们也在持续迭代优化。欢迎大家使用，并提出宝贵反馈。
