# ADR 与 SDD：从架构决策到代码落地的闭环

从一个常见现象说起 每个做过一段时间的团队都经历过这样的场景：一个方案上线半年后出了问题，新来的同学问"当初为什么要这么设计"，老同学回答"开了个会讨论的，好像是因为 XXX，但我也记不太清了"。或者更常见的：两年前的架构评审定了一个技术选型，现在条件变了想改，但没人说得清当初的约束条件是什么、还有没有备选方案、当时否掉其他方案的理由是否还成立。 这些问题在大规模基础设施团队尤其严重。架构决策通常具有高度不可逆性——一个架构方案选定之后，要推翻它的成本远高于从头设计。但恰恰是这些影响深远的决策，往往只存在于少数人的脑中，或者散落在会议纪要和钉钉群聊里。 这不是个新问题。2011 年，软件架构师 Michael Nygard 提出了 Architecture Decision Records（ADR）这个概念来解决它。但直到最近，ADR 才因为 AI 辅助研发的兴起获得了新的生命力——因为 ADR 不仅是给人看的文档，它还是给 AI coding agent 提供架构上下文的最佳载体。 本文整理了近期对 ADR 的调研，核心想讲清楚三件事：ADR 是什么、为什么现在值得认真对待、以及它如何与当前火热的 Spec-Driven Development 形成闭环。 一、ADR 的本质：把"为什么"从人的脑子里搬出来 定义 微软 Azure Well-Architected Framework 对 ADR 的定义是目前最精确的： "Your architecture is the accumulation of its decisions, so the ADR is effectively a record of how and why the system came to be its current shape." （你的架构是其所有决策的累积，ADR 是记录系统为何演变为当前形态的档案。） 简单说：ADR 不是设计文档（那是"怎么做"），不是需求文档（那是"做什么"），而是决策文档——"为什么选了 A 不选 B，当时的约束条件是什么，做了哪些取舍"。 一条标准 ADR 长什么样 从 Google Cloud、AWS、Microsoft Azure 三家的实践来看，一条标准 ADR 包含以下核心字段： 字段 内容 作用 Status Proposed / Accepted / Superseded 追踪决策生命周期 Context 当前面临的技术挑战、系统约束、业务需求 说明"为什么要做这个决策" Options Considered 所有评估过的备选方案 记录选择范围 Decision 最终选定的方案及核心理由 明确"选了什么、为什么" Consequences 选定方案带来的正面收益和负面代价 暴露 trade-off Confidence Level 做出决策时的信心程度 标记哪些决策未来可能需要重新审视 微软特别强调了两个关键设计原则： Append-only log：ADR 是只追加的日志，已接受的记录不可修改。如果决策变了，写一条新的标记为"Supersedes"，保留完整的演进历史。 记录 confidence level：有时候重大决策是在信息不完备的情况下做出的。标记低置信度为未来的 revisit 提供触发信号。 三大云厂商都在正式推荐 ADR 这不是一个小团队的实验性实践： Google Cloud 在架构文档中明确建议：当团队面临没有现有依据的技术挑战、或需要在多个工程路径间选择时，创建 ADR（Google Cloud Architecture Guide）。 AWS 在 Prescriptive Guidance 中发布了完整的 ADR 流程指南，强调"promote ownership"——不只是架构师写，每个团队成员都可以创建和 own ADR（AWS Prescriptive Guidance）。 Microsoft Azure 在 2026 年 4 月更新的 Well-Architected Framework 中，把 ADR 定位为"解决方案架构师最重要的交付物之一"（Microsoft Learn）。 二、为什么现在值得认真对待 ADR：AI Coding 时代的新价值 ADR 的传统价值（知识传承、避免重复讨论、降低 onboard 成本）已经被讨论很多了。这里重点讲一个新的、在 AI coding 时代才凸显的价值。 ADR 是 AI Coding Agent 的"隐性知识显性化"工具 一篇 2025 年 5 月的 arXiv 论文（Context-Augmented Code Generation: How Product Context Improves AI Coding Agent Decision Making）做了一个直接的实验： Baseline（AI agent 只有代码库访问权限）：架构决策合规率 46% Augmented（AI agent 额外获得 ADR 等产品上下文）：架构决策合规率 95% 进一步分析发现：baseline agent 在"代码可见的规则"上能达到 100% 合规（因为它可以从已有代码中推断），但在"代码不可见的 gotcha 决策"上只有 0-33%（因为这些决策只存在于团队的隐性知识中）。注入 ADR 后，这些 gotcha 决策的合规率飙升。 论文的核心结论："The codebase tells an agent what exists; product context (including ADR) tells it what should exist." 这意味着：如果你希望 AI coding agent 不只是生成"能跑的代码"，而是生成"符合团队架构意图的代码"，那 ADR 就是你必须提供给 agent 的关键上下文。没有 ADR，agent 只能从现有代码中猜测规则；有了 ADR，agent 能理解"为什么要这样设计"以及"什么是不可逾越的架构底线"。 实际效果：成本下降 68% 同一篇论文还发现，注入 ADR 等架构上下文后，每个 merge-ready task 的成本下降了 68%，blocking violations 降为 0。这不是"锦上添花"，而是直接影响研发效率的数据。 三、ADR 与 Spec-Driven Development 的关系：一个分工明确的上下游闭环 核心关系：ADR answers WHY, Spec answers WHAT 这是理解两者关系最重要的一句话。它们不是竞争关系，不是替代关系，而是正交互补： 维度 ADR Spec (SDD) 回答什么问题 WHY——为什么选了这个方案 WHAT + HOW TO VERIFY——具体做什么、怎么验证 介入时机 决策确认后（post-decision） 代码实现前（pre-implementation） 生命周期 静态固化（一次写入，极少修改） 动态演进（随实现迭代更新） 粒度 系统级（架构选型、技术栈、核心约束） 模块级（特性实现、API 定义、边界条件） 给谁看 架构同学、核心研发、后续维护者 执行实现的研发同学和 AI coding agent 完整的上下文闭环：给 AI Agent 的"What + Why + How to Verify" 当两者结合使用时，AI coding agent 获得了完整的上下文： ADR（WHY）→ 约束 Spec 的边界
     ↓
Spec（WHAT + HOW TO VERIFY）→ 指导 AI Agent 实现
     ↓
Code Review（AI 检查代码是否符合 ADR 约束 + Spec 规范）
 引用 CEAKSAN 原文的表述："When used together in AI-assisted development, they provide complete context: what + why + how to verify." 这三要素的闭环使得 AI 从"概率生成"转向"确定性编译"——不再需要猜测团队的架构意图。 四、落地思路：在我们的场景中怎么操作 问题一：架构决策都是开会讨论出来的，怎么规范化产生 ADR？ 这是最现实的问题。我们的现状是：大量架构决策产生在评审会议、方案讨论群聊、一对一技术讨论中。要求架构同学"每次开会后额外写一份 ADR"，大概率会变成形式主义。 几种可行的落地路径，按轻量程度排序： 路径一：会议纪要 → AI 结构化 → ADR 草稿 → 人确认 最低成本的方式。现有的方案评审会议本来就有纪要，用 LLM 从纪要中提取架构决策相关的内容，按 ADR 模板结构化输出草稿，架构同学只需 review 确认。这相当于把"写 ADR"的工作从"创作"变成了"审阅"，认知负担大幅降低。 Equal Experts 团队实践过类似方法，他们的经验是"We might generate dozens of ADRs in a single morning"——效率远超人工撰写（Equal Experts Blog）。 路径二：把 ADR 作为方案评审的必选 output 稍重一些但更规范：要求每个方案评审会议的 output 中必须包含至少一份 ADR（如果做了架构层面的决策的话）。ADR 可以由 AI 从讨论内容中生成初稿，评审参与者确认后即为正式版本。这把 ADR 嵌入了已有流程，而不是额外流程。 路径三：Salesforce 的 Prompt Chaining 5 步法 适合即将做出的重大决策（事前）。在决策过程中就按结构化方式进行：AI 生成评估标准 → 架构同学修正 → AI 做方案对比矩阵 → 架构同学挑战假设 → AI 生成 ADR（Salesforce Blog）。 对于存量历史决策的补录，AWS 建议采用 retroactive generation：在信息还可获取时（相关人员还在、文档还在），批量回溯生成历史 ADR。 问题二：产生的 ADR 怎么与 Spec-Driven AI Coding 结合？ 这是更前沿的问题，目前行业的实践还在早期，但方向已经比较清晰。基于调研，我认为结合路径大致分三步： 第一步：ADR 作为 Spec 的输入约束 写 Spec 时，引用相关 ADR 作为约束条件。比如 Spec 中声明"本模块的实现必须遵循 ADR-007 中关于数据面转发路径的约束"。这使得 Spec 编写者和 AI agent 都能明确知道哪些边界不可逾越。 第二步：ADR 作为 AI Agent 的 context injection 在 AI coding agent 执行任务时，通过 RAG 或直接注入的方式，把相关的 ADR 加入 agent 的上下文。arXiv 2605.08112 的实验已经证明这能把合规率从 46% 拉到 95%。具体实现上，可以参考 Claude ADR System（GitHub Gist）的做法——在代码仓库中维护 ADR 索引，agent 工作时自动检索相关决策。 第三步：ADR 作为 Code Review 的合规基线 AI code review 时，检查代码变更是否违反了已有的 ADR 约束。Shing Lyu 2026 年 3 月的一篇实践（ADR in Code: Architecture Compliance with AI Code Reviews）描述了具体做法：把 ADR 作为 review rules 的输入，AI 自动检测违规。 三步合在一起，ADR 就从"静态文档"变成了"活体架构约束"——它不只被人阅读，还被 AI 解析和执行。 五、一些开放问题 上面是基于当前调研的初步思路，但仍有一些需要进一步探索的问题： ADR 的粒度怎么控制？ 云网络的架构决策从"选用什么组网方案"（极粗）到"某个接口的超时时间设多少"（极细）都有，哪些值得写 ADR、哪些不值得？微软的建议是"只记录影响系统结构、关键质量属性、或难以逆转的选择"，但在实践中这条线怎么画需要团队共识。 ADR 和已有的方案设计文档怎么共存？ 我们已经有了很多方案设计文档（包含详细设计），ADR 和它们的关系是什么？微软明确说"ADR 不是设计指南"——它只记录决策和理由，详细设计作为补充材料链接引用。但这种分离在实践中能不能维持？ 从讨论到 ADR 的自动化程度能做到多高？ 目前从会议录音/转写自动提取架构决策的技术还在早期。如果能做到"开完评审会，AI 自动给你一份 ADR 草稿等你确认"这样的体验，落地阻力会非常小。 ADR 知识库怎么与 AI Agent 高效对接？ 当 ADR 积累到一定规模后，怎么让 AI agent 在需要时快速找到相关的决策？这涉及 ADR 的标签化、向量化和检索机制的设计。 六、参考资料 云网络竞品分析助手辅助分析： ADR, OpenSpec and Spec-Driven Development: Decision and Spec Management ADR in Code: Architecture Compliance with AI Code Reviews |
