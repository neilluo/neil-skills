基于 EP/PD 分离架构的 DeepSeek-R1-671B 推理优化实践 Part 1: 导论 1. 这篇文章讲什么 一句话总结：我们把一个6710亿参数的超大AI模型拆成两部分运行，让响应速度更快、成本更低。 为什么要这样做： 传统方式：AI回答问题时，"理解问题"和"生成答案"抢资源，互相拖后腿 新方式（PD分离）：把这两步分开，Prefill和Decode各干各的 2. 为什么写这篇文章 2.1 真实项目背景 2025年9月，中国移动集团计划建设部、研究院与苏研质量部组织了一场智算推理池PD分离性能测试。PD分离高网部署实战详见 SA动手系列1-PD分离-部署到测试实战手册。 3. 大模型推理的两阶段特性 3.1 什么是Prefill和Decode？ 大模型推理分为两个阶段：Prefill（理解问题阶段）和Decode（生成答案阶段）。 Prefill阶段：系统读取并理解用户的完整问题，在GPU上做大量计算，生成"记忆"（KV Cache）。这一阶段是计算密集型，类似于"阅读理解"考试。 Decode阶段：根据Prefill阶段的理解，逐字生成回答，每次只生成一个字（token），需要不断引用"记忆"来保持上下文连贯。这一阶段是内存密集型，类似于"写作文"。 举例：用户问"请帮我写一篇关于人工智能的文章"，系统先在Prefill阶段理解这个请求并生成KV Cache，然后在Decode阶段逐字输出"人工智能（AI）是计算机科学的一个分支..." 3.2 Prefill vs Decode 对比表 对比维度 Prefill（理解阶段） Decode（生成阶段） 工作内容 读取理解问题 逐字生成回答 计算特点 计算密集型 内存密集型 GPU利用率 Tensor Core高负载 显存带宽瓶颈 延迟指标 TTFT（首字延迟） TPOT（每字延迟） 通俗比喻 阅读理解 写作文 4. 传统架构的问题 4.1 问题示意图 传统PD耦合架构下，Prefill和Decode跑在同一组GPU上。Prefill阶段会抢占计算资源，而Decode阶段则被阻塞，两者争抢资源。 核心问题： 资源争抢：Prefill抢计算单元，Decode被阻塞 扩缩容困难：两阶段负载不同，难以统一调度 延迟不稳定：长问题理解会阻塞短答案生成 问题详解： 传统架构下，Prefill和Decode跑在同一组GPU上，看似省资源，实际问题不少： 资源争抢 Prefill阶段要处理完整输入序列，计算量大，会把Tensor Core占满 这时候Decode阶段的请求只能等着，GPU利用率看着高，实际吞吐量上不去 我们实测发现，一个长请求的Prefill可能耗时2-3秒，期间所有短请求都在排队 扩缩容困难 Prefill和Decode对资源的需求差异很大 Prefill计算密集，需要高算力；Decode内存密集，需要大显存 绑在一起扩容，要么浪费算力，要么浪费显存 延迟不稳定 长请求的Prefill会阻塞短请求的Decode 用户发了个简单问题，结果等了好几秒才出第一个字 体验很差，而且抖动大，难以预估性能 5. PD分离架构 5.1 系统组件图 PD分离架构包含四个核心组件： 用户请求流程：用户请求 → Router（mini_lb负载均衡，将请求分发到对应集群）→ Prefill集群或Decode集群 Prefill集群：配置TP8，计算密集型，负责生成KV Cache。处理完成后，通过GPUDirect RDMA直传将KV Cache传送到Decode集群。 Decode集群：配置DP8+EP16，内存密集型，负责逐token生成答案。 配置参数：PTPSIZE=8, PMEMFRACTION=0.9; DDPSIZE=8, DEPSIZE=16, DMEMFRACTION=0.8 组件职责详解： 组件 职责 通俗理解 Router 请求调度、负载均衡 餐厅经理，安排座位 Prefill集群 理解问题、生成KV Cache 点菜员，记录顾客需求 Decode集群 逐字生成回答 厨师，根据菜单做菜 KV Cache传输层 高速传递"记忆" 传菜员，传递订单信息 工作流程： 请求接入 用户请求先到Router Router判断请求类型，决定分发到哪个集群 短请求可能直接走Decode，长请求先走Prefill Prefill处理 接收完整输入序列 并行计算生成KV Cache KV Cache准备好后，通知Decode集群 KV Cache传输 通过GPUDirect RDMA直接从Prefill GPU传到Decode GPU IB网络链路延迟微秒级，端到端传输延迟取决于KV Cache大小 200Gbps带宽，传输速度有保障 Decode生成 从KV Cache开始，逐token生成答案 多个请求并行处理 输出结果返回给用户 6. 关键技术优化 6.1 KV Cache传输优化 KV Cache传输流程：Prefill GPU生成KV Cache（AI的"记忆"，理解结果）→ 通过GPUDirect RDMA直传（200Gbps带宽）→ Decode GPU接收KV Cache用于生成。 优化效果： GPUDirect RDMA直传：GPU显存间直接传输，避免CPU中转 流式传输：Prefill部分完成即开始传输 什么是KV Cache？ 简单说，KV Cache就是AI的"记忆"。Prefill阶段把用户的输入理解完，生成一个中间状态存起来，这个中间状态就是KV Cache。后面Decode阶段生成答案的时候，需要不断引用这个记忆来保持上下文连贯。 为什么传输优化很重要？ KV Cache大小跟输入长度成正比，64K上下文的KV Cache可能达数十GB（取决于模型架构和量化策略） 如果传输慢，Decode就要等，整体延迟就上去了 传统方式要经过CPU中转，我们用RDMA直接GPU到GPU 三项优化措施： GPUDirect RDMA直传 GPUDirect RDMA技术，GPU显存通过网卡直接DMA通信 数据路径：源GPU→源HCA→IB网络→目标HCA→目标GPU，全程无需CPU介入 IB网络链路延迟微秒级，端到端传输延迟取决于KV Cache大小 FP8量化压缩 KV Cache从BF16压缩到FP8 数据量减半，传输时间减半 精度损失实测 < 0.1%，可以接受 流式传输 Prefill不用等全部完成 每处理完一部分就传一部分 Decode可以提前开始，进一步降低延迟 6.2 Chunked Prefill优化 问题：长文本（如14K+字符）可能导致显存不足（OOM） 两种处理方式对比： 不分块（风险高）：一次性加载全部文本（14K+字符），风险是显存不足，程序崩溃。 分块处理（推荐）：将文本分成多个Chunk（如Chunk1: 10K字符、Chunk2: 10K字符、Chunk3: 剩余），分别处理后合并。这样可以稳定处理，无OOM风险。 实测数据（DeepSeek-R1-671B，W8A8量化）： 序列长度 不分块状态 Chunked Prefill 延迟影响 16K 偶发OOM 稳定运行 +3.2% 32K 频繁OOM 稳定运行 +5.7% 64K 无法运行 稳定运行 +7.8% 128K 无法运行 稳定运行 +9.1% 分块策略详解： 为什么要分块？ 长文本一次性加载，KV Cache瞬间占满显存 32K以上几乎必OOM，服务直接挂掉 分块可以控制峰值显存占用 分块大小怎么选？ 分块大小取决于显存容量和序列长度 太小会频繁切换，增加调度开销 太大还是可能OOM 我们实测10K-128K均可，根据实际显存调整 延迟影响多大？ 有代价，但可控 64K场景延迟增加约7.8% 相比无法运行，这个代价完全可以接受 配置参数： # 推荐配置

GPU 15：专家 241-256 优势： 显存效率：每张卡只存16个专家（1/16），单卡96GB放16个专家绰绰有余 计算效率：只有被激活的专家参与计算，其他GPU可以处理其他请求 EP并行原理： DeepSeek-R1是MoE模型，有256个路由专家和1个共享专家。每次推理激活8个路由专家和1个共享专家（共9个）。EP（Expert Parallelism）就是把不同路由专家放到不同GPU上，共享专家则复制到所有GPU。 专家分布策略： GPU 存储的专家编号 GPU 0 专家 1-16 GPU 1 专家 17-32 ... ... GPU 15 专家 241-256 为什么这样设计？ 显存效率 256个专家，如果每张卡都存全部，显存不够用 EP16后，每张卡只存16个专家，显存压力大幅降低 单卡96GB，放16个专家绰绰有余 计算效率 每次推理只有8个专家被激活 只有存了这8个专家的GPU需要工作 其他GPU可以处理其他请求，利用率高 通信开销 专家之间需要AllReduce通信 EP模式下通信模式相对简单 配合RDMA，延迟可控 7.3 并行策略决策过程 7.3.1 Prefill阶段：为什么选择TP8？ 决策过程： Prefill阶段的TP8配置基于三个关键因素的综合考量： 计算特性：Prefill是计算密集型，需要高算力切分。TP并行可以有效利用多卡，Tensor Core利用率可达95%+。 显存需求：671B参数经FP8量化后约671GB，单卡96GB，8卡总显存768GB。模型权重约占87%，剩余空间用于KV Cache、激活值和CUDA上下文。启用MEM_FRACTION=0.9限制实际使用，为运行时预留缓冲。 通信开销：TP需要频繁AllReduce，TP8在可接受范围内。TP16会显著增加通信延迟（约增加40%）。 综合以上因素，TP8是最佳平衡点。 决策因素详解： 因素 具体分析 数值依据 计算特性 Prefill阶段需要处理完整输入序列，计算量大 Tensor Core利用率可达95%+ 显存需求 671B参数经FP8量化后约671GB 8卡总显存768GB，权重占87%，预留运行时开销 通信开销 TP需要频繁AllReduce，TP8在可接受范围 TP16通信延迟增加约40% 7.3.2 Decode阶段：为什么选择DP+EP？ 决策过程： Decode阶段的DP+EP配置基于三个关键因素的综合考量： 显存特性：Decode是内存密集型，KV Cache随序列增长，需要更大显存空间。 MoE特性：256路由专家+1共享专家天然适配EP16，每张卡存16个路由专家（共享专家复制），显存效率高。 并发需求：多请求并行，DP提供多副本并行，EP配合高效调度。 实测配置：DP8 + EP16 配置组合解析： 配置项 作用 效果 DP8 8路数据并行 吞吐量提升约8倍 EP16 专家并行 每卡只存16个路由专家，显存效率高 7.4 踩坑经验 问题 现象 解决方案 显存不足 OOM错误，服务崩溃 降低MEM_FRACTION或增加TP 通信超时 NCCL超时，训练中断 检查网络配置，增加超时时间 负载不均 部分GPU空闲，利用率低 调整DP/EP配比 KV Cache传输慢 TTFT过高 检查RDMA配置，优化网络拓扑 Part 2: 实验与分析 8. 测试结果 8.1 核心指标说明 指标 含义 为什么重要 Decode单卡吞吐 单张GPU的输出速度 直接反映性价比 TTFT 首字延迟 用户等多久看到第一个字 TPOT 每字延迟 用户等每个字的时间 系统并发 同时处理的请求数 系统承载能力 8.2 全场景测试结果 场景 输入 输出 TTFT(ms) TPOT(ms) Decode单卡 系统并发 短文本 20 512 451 54 192 340 1K 512 512 447 67 204 441 2K 1K 1K 469 54 159 278 4K 3K 1K 907 58 129 243 8K 4K 4K 978 80 118 301 16K 2K 14K 576 82 90 236 32K 4K 28K 839 92 74 273 64K 8K 56K 2569 87 34 119 10. PD配比优化 10.1 什么是PD配比？ PD配比指Prefill节点数与Decode节点数的比例，不同配比适合不同场景。 10.1.1 短输入均衡场景 1P3D配置：1个Prefill节点（TP8）+ 3个Decode节点。 数据流向：Prefill节点生成KV Cache后，分别传输到3个Decode节点进行生成。 特点：输入长度与输出长度相近，Decode并发需求大，需要更多D节点。典型业务：客服问答、实时对话。 10.1.2 长输入短输出场景（RAG/分析类） 2P1D配置：2个Prefill节点 + 1个Decode节点。 数据流向：2个Prefill节点并行处理，生成的KV Cache合并传输到1个Decode节点。 特点：输入长度长导致Prefill计算量大，需要更多P节点处理输入。输出较短，D节点需求相对较少。典型业务：RAG检索增强生成、文档分析、论文摘要。 10.1.3 短输入长输出场景（代码生成/写作类） 1P4D或1P8D配置：1个Prefill节点 + 4-8个Decode节点。 特点：输入长度短、输出长度长，Decode生成密集，需要更多D节点。Prefill计算量相对较小，但Decode需要长时间生成。典型业务：代码补全、创意写作、长文生成。 10.1.4 配比计算方法论 核心原则： 输入长度：决定Prefill阶段计算量，输入越长 → Prefill压力越大 → 需要更多P节点 输出长度：决定Decode阶段生成时间，输出越长 → Decode压力越大 → 需要更多D节点 我们采用基于业务特征的初始配比计算方法，而非经验估算： 计算公式： 公式解读： 分子（输入长度 × Prefill单token时间）：代表Prefill阶段的计算压力 分母（输出长度 × Decode单token时间）：代表Decode阶段的生成压力 Ratio > 1：Prefill压力大，需要更多P节点 Ratio < 1：Decode压力大，需要更多D节点
