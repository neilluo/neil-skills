## 二、口径纠正：孙佳毅的断言站不住

### 断言原文（9/20 16:20）
> 「您如果能接受http转mcp类型的mcp服务 tools/call请求能外部认证插件处理就可以的，如果想初始化及 tools/list也要走外部认证插件处理这个不行」

### 三层反证

**① 官方原文直接冲突。**《调试MCP服务》（help.aliyun.com/zh/api-gateway/ai-gateway/user-guide/debug-mcp-services，我已 curl 核实第 29 行）：
> 「如果所选消费者只授权了 MCP工具级别消费者认证，且仅授权某些工具的情况下，**HTTP转MCP的场景中获取工具列表只能看到和调用有权限的工具**；直接代理场景调试的时候能看到全部工具，选择授权的工具调用是ok的，没权限的会403。」

→ 官方文档明写：HTTP转MCP 下工具级鉴权**就是作用于 tools/list 的**（表现为按权限过滤）。

**② 架构上不自洽。** MCP 规范把鉴权放在**传输层**，Streamable HTTP 强制「单一 MCP endpoint，每条 JSON-RPC 消息都是一次新的 HTTP POST」。`initialize`/`tools/list`/`tools/call` 在 HTTP 层同 path 同 method，而 ext_authz 是跑在 MCP 协议解析之前的 HTTP filter——**物理上无法区分方法**。"某方法能、某方法不能"只可能发生在鉴权被挂到 MCP 语义层（按 MCP 服务/工具挂消费者认证）时。

**③ 官方文档零命中。** AI 网关 llms.txt（123KB 全量索引）、云原生API网关 llms.txt（138KB）、MSE llms.txt（308KB）中 `ext-auth`/`外部认证`/`service_name` **全部 0 命中**；官方认证插件清单只有 6 个（key-auth/basic-auth/hmac-auth/jwt-auth/jwt-logout/oauth），**不含 ext-auth**；抓取的 8 篇 MCP/认证官方文档 + 发布记录 + 引擎版本说明中 `tools/list`/`initialize`/`tools/call` **全部 0 命中**。ATA 全站检索 `ext-auth` **0 命中**、`网关MCP鉴权` **0 命中**——**内部也没有任何书面实测记录支撑这句话**。

### 我的判断
`[推断]` 他很可能是把「MCP **工具级**消费者认证」的现象（按工具授权，直接代理模式下 tools/list 返回全部工具、调用才 403）错误迁移到了 ext-auth 上。**不是恶意，是概念串台**——但客户拿到的是一个"产品做不到"的结论，而这个结论是错的。

## 五、给产研的需求（按实现成本排序）

**P0 —「自建认证鉴权」增加鉴权路径匹配模式（成本最低、收益最直接）**
现状：控制台「鉴权API」只有前缀拼接语义（官方原文：「API的Path需是前缀匹配」「真实Path是鉴权API加上原始业务请求的Path后的结果」）。
需求：增加选项「前缀拼接 / **精确固定路径**」。
🔴 **关键论据：Higress 开源 ext-auth 早就有这个能力**（`endpoint_mode: forward_auth` = 固定 path + 可配 method + 原始路径走 `X-Forwarded-Uri` 头），**阿里云控制台只暴露了等价的 `envoy` 模式**。这不是架构改造，是把自家开源已有能力透出到控制台。
配套：暴露「认证请求 HTTP Method」配置项（火山有，我们没有）。

**P1 — 明确并文档化 MCP 各方法的鉴权覆盖范围**
现状：官方文档在 `tools/list`/`initialize`/`tools/call` 上零表述，导致一线售后只能凭理解答复客户，已经答错一次。
需求：在 AI 网关 MCP 文档里明确「HTTP转MCP 下鉴权作用于哪些协议阶段」，并把《调试MCP服务》里已有的工具级过滤行为写进鉴权章节。

**P2 — ext-auth 插件的官方文档缺位**
现状：三条产品线官方文档全量索引 0 命中，官方认证插件清单不含 ext-auth，但插件市场里客户能看到「外部认证」并正在用。**客户查不到文档、售后查不到口径、工单没有依据**——这是本次事件拖了 4 天的根本原因之一。
需求：要么把 ext-auth 纳入官方插件文档，要么在控制台插件详情页直接内嵌 Higress 文档链接与版本对应关系。

**P3 — 澄清官方文档自相矛盾**
`consumer-certification.md` 称「认证方式目前仅支持 API Key」，发布记录 2026-01 称「MCP Server 支持 JWT 认证」→ 文档口径滞后，需统一。

## 六、火山对标（客户 9/18 明说在调研，附了一张 430×717 截图，我拿不到）

### 客户那句话文档有据，不是话术
`[竞品官方]` 火山「外部认证鉴权」插件（volcengine.com/docs/6569/1798159）：**认证地址自由路径**（示例 `/`）、**认证方法可选 GET 或 POST**、认证位置可配 header（示例就是 `Authorization`）、匹配规则支持**精确匹配**、原始 Path **走 header 传递**（「客户端的 `Host`、`Method`、`Path` 和 `Content-Length` 请求头会默认添加至鉴权请求报文中」）。
→ 客户的 `GET /api/mcp/personal-tokens/verify` 在火山上确实零改动。**差距真实存在，且是本次事件的直接技术原因。不护短。**

### 但火山有两条客户可能不知道的硬约束（你的反击点）
`[竞品官方]` 同一文档明写：
1. 自建认证鉴权「当前**仅支持在实例级别生效**」（我们支持 MCP/路由级 → 域名级 → 实例级三级）
2. 自建认证鉴权服务所在的云资源（VKE/ECS 等）「**必须与 API 网关实例在相同私有网络**」

→ **客户的认证接口是公网域名，同 VPC 这条很可能直接卡死他。** 建议让他在火山 POC 时先验这一条，别等我们这边解完了他那边才发现走不通。
另外 `[竞品官方]` 火山「什么是 AI 网关」文档还挂着**【邀测·申请试用】需联系客户经理**——并非全面可用的成熟形态。

### 别丢掉我们更强的一张牌
决定「哪些请求需要鉴权」的**授权规则表达力**上：我们支持 精确 / 前缀 / **正则 Re2** + 请求头 9 种操作符 + **复杂条件（Envoy permission YAML，与/或/非组合）**；火山只有 前缀 / 精确。客户全程没提这块，但费控 SaaS 做多租户按域名/路径分级鉴权时这是硬需求。

### 技术底座同源 → 这是实现选择，不是平台代差
火山官方明写「采用 Envoy 内核」；我们是 Higress 系（Envoy-based），文档直接引用 Envoy 官方 permission 结构、暴露 `x-mse-external-authz-check-result` 头；Higress ext-auth 文档明写「参考了 Envoy 原生的 **ext_authz filter**」。**同源**。所以对客表述应该是"这个能力我们有、只是控制台还没透出"，而不是"我们做不到"。
