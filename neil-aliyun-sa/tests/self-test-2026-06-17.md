## 测试 1（模式 F — 1 分钟洞察）

**Query**：百炼和 PAI 怎么选？给客户 30 秒解释清楚。

**走查路径**：
1. `knowledge/aliyun-products.md` → AI 章节 → 百炼能力卡 + PAI 能力卡（命中）
2. `references/cloud-product-mapping.md` → AI/大模型场景表（命中）
3. `knowledge/ai-trends.md` → 百炼 vs PAI 边界（命中，已经特意写过这一对的差异）

**产出**：
> 百炼是"调模型用"，PAI 是"训模型用"。业务方直调 → 百炼（MaaS，按 token 计费）；自己微调或训练 → PAI（DLC 训练 + EAS 部署 + GPU 资源池化）。典型客户百炼跑 80% 应用，自训模型扔到 PAI-EAS。

**评分**：
- 速度 ✅ < 30 秒
- 准确性 ✅ 三处来源交叉印证
- 完整性 ✅ 涵盖 MaaS / 自持 / 边界
- 缺什么：无

**结论**：✅ 通过。模式 F 是 skill 当前的强项。

## 测试 2（模式 C — 产品选型）

**Query**：物流 SaaS，订单峰值 5000 TPS，要从 RDS 迁 PolarDB 还是 PolarDB-X？

**走查路径**：
1. `knowledge/aliyun-products.md` → 数据库章节 → RDS / PolarDB / Lindorm 三张能力卡（命中 RDS、PolarDB；缺 PolarDB-X 独立卡）
2. 数据库选型决策树（命中，但简略）
3. `references/cloud-product-mapping.md` → "OLTP 数据库" → "单机 vs 分布式"（命中关键词，缺 5000 TPS 这个量级的具体推荐）

**产出**（基于知识库 + 经验补丁）：
> 5000 TPS 是临界值——单机 PolarDB 高规格能扛住（推荐 32c256g + 多只读节点），先不上 PolarDB-X。
>
> - **现阶段建议 PolarDB MySQL**：存算分离、最大 100TB、读写分离 + 全局一致性读，迁移成本最低（DTS 一把梭）
> - **什么时候上 PolarDB-X**：单实例写入压垮（>20000 TPS）、单库容量 >100TB、强分库分表诉求、跨地域多活
> - **风险点**：PolarDB-X 分布式事务有性能折损，订单流水强事务场景慎选

**评分**：
- 速度 ✅ ~2 分钟
- 准确性 ⚠️ "5000 TPS 临界值"、"PolarDB-X 切换时机 20000 TPS"是经验推断，知识库无明确条目
- 完整性 ⚠️ 未触达细节：sharding key 设计、DTS 迁移停机窗口、PolarDB Serverless 是否合适

**缺口清单**：
- ❌ PolarDB MySQL 单实例 TPS / 容量 上限 没写在能力卡
- ❌ PolarDB-X 没单独的能力卡（只在数据库决策树里出现一行）
- ❌ "什么时候从 PolarDB 切到 PolarDB-X" 这种**升级阈值**没沉淀
- ❌ DTS 在生产数据库迁移中的实战参数（停机窗口、限速、回退）

**结论**：⚠️ 通过但有补丁。给客户讲不致命，但**证据等级是 [推断]，不是 [官方]**——SKILL.md 跨源验证规则要求标注，自答时容易漏掉。
