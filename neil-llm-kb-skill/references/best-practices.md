# LLM Wiki 最佳实践（来自阿里内部 ATA 高质量实践）

> 来源：KBase 平台实践（3861浏览/翰林院推荐）、Compass 天基知识库（653浏览/33赞）、跨域复用验证（445浏览/24赞）

---

## 1. 编译思维 vs 检索思维（核心范式区分）

| 维度 | RAG（检索模式） | LLM Wiki（编译模式） |
|------|----------------|---------------------|
| 知识组装时机 | 查询时临时拼凑 | **提前编译好**，随时可用 |
| 状态性 | 无状态，每次从零推导 | **有状态**，知识持续积累 |
| 文档处理 | 片段化切割，语义割裂 | 全文理解，重构知识网络 |
| 增量更新 | 追加入库，无知识关联 | **增量编译**，自动更新交叉引用 |

**核心隐喻**：RAG 像每次都拆快递箱找东西的仓库，LLM Wiki 像已分类收纳好、贴好标签的柜子。

---

## 2. 多对一映射（最有价值的能力）

**LLM Wiki 最有价值的能力不是"1篇文档生成1篇Wiki"，而是多篇原始文档编译为同一篇主题页。**

这体现了从"情景记忆"到"语义记忆"的映射：
- 5 篇关于认证的散落文档 → 编译为 1 篇《认证模块总览》
- 72 篇 QCon 分享文档 → 编译为 14 个主题 Wiki 页面

每篇 Wiki 保留对每篇源文档的精确引用，实现可追溯的知识压缩。

**实践规则**：Ingest 时不应做 1:1 映射，而应识别跨文档的共同主题，将多个源聚合到同一个 Wiki 页面。

---

## 3. 两阶段编译（Compass 验证的最优策略）

**不要在一个步骤中同时做分类和内容生成。**

| 阶段 | 做什么 | 不做什么 |
|------|--------|---------|
| **Stage 1: 分类** | 判断一篇原始文档会贡献到哪些 Wiki | 不抽取/压缩具体内容 |
| **Stage 2: 生成** | 把完整原始文档 + 已有 Wiki 一起给模型，生成新版本 | 不依赖中间态摘要 |

**为什么这样做**：如果在分析阶段同时做"判断写到哪篇 Wiki"和"抽取相关内容"，长文档里的字段含义、配置关系、边界条件等细节会在中间抽取时被压缩或遗漏，后续生成阶段无法恢复。

---

## 4. AI 审核门禁（防止知识污染）

**知识发布前必须有质量门禁，避免错误内容进入正式知识库。**

审核检查维度：
- 是否忠实于原始材料
- 是否引入了原文没有支持的结论
- 是否遗漏了关键约束
- 是否存在前后矛盾
- 是否把临时/猜测性内容写入正式知识

**审核闭环**：审核问题 → 反哺到编译 Prompt → 后续生成更稳定

审核不通过的内容**不进入正式搜索和 RAG 链路**，带着审核反馈重新生成。

---

## 5. Schema = 人和 AI 的契约

Schema 不是数据结构定义，而是知识库的"宪法"：

| Schema 约束的 | 示例 |
|--------------|------|
| 主题范围 | 这个知识库覆盖什么领域 |
| 编译规则 | 如何从 Raw 生成 Wiki |
| 查询规则 | Agent 如何使用 Wiki 回答 |
| 健康检查规则 | Lint 检查什么 |
| 命名规范 | 文件名、slug、前缀规则 |

**关键洞察**：Schema 约束行为，不约束分类。不预设"应该有哪些 Topic"，让 Topic 在 Ingest 中自然涌现。

---

## 6. 首次编译不必一步到位

当原始资料较多时，不要期望一次编译就生成完整 Wiki。

**推荐做法**：
1. 先让 Agent 对一部分核心资料做首轮编译
2. 检查结果后指出遗漏的方向
3. 引导 Agent 补充
4. 后续新增文档只需增量编译

Agent 会在已有 Wiki 结构上持续扩展，不必每次从头来过。

---

## 7. RAG 和 LLM Wiki 是互补关系

| 场景特征 | 推荐方案 |
|---------|---------|
| 海量文档、高并发 | RAG |
| 合规溯源、原文保真 | RAG |
| 个人知识管理、小团队 | LLM Wiki |
| 中等规模、需要深度理解 | LLM Wiki |
| 跨文档综合推理 | LLM Wiki |
| 海量文档 + 概念级理解 | **RAG 底座 + Wiki 上层** |

**双层知识结构**：原始文档负责细节级检索，Wiki 层负责结构化导航和全局视图。两者各司其职。

## 8. 三大关键设计决策

### 决策 1: Raw 不可变

- LLM 绝不修改 raw/ 下的任何文件
- 直接好处：溯源可靠
- 深层好处：天然适配增量编译——新素材进来只需增量更新 Wiki

### 决策 2: 关系用双向链接，不用显式图谱

- ❌ YAML/JSON 显式建模关系 → 双重维护、LLM 不擅长精确编辑嵌套结构
- ✅ [[双向链接]] → 单一数据源、Obsidian 友好、LLM 友好

**本质**：让工具链决定关系表达方式。工具链是 LLM + Markdown → 双向链接最自然。

### 决策 3: Schema 约束行为，不约束分类

- ❌ 预设"应该有哪些 Topic/Entity 类型"
- ✅ 约束页面模板、文件命名、操作流程

新领域的知识体系无法预测，但操作流程可以标准化。

## 9. Prompt = Schema 的工程表达（Compass 实践）

Prompt 不是几句角色设定，而是知识库的核心机制：

### 构建阶段 Prompt：定义 Wiki 如何生成
- 配置文件类 Wiki：聚焦字段、格式和约束
- 场景类 Wiki：聚焦可复用的操作流程
- 概念类 Wiki：聚焦机制、边界和设计背景
- 故障排查类 Wiki：聚焦症状、检查方法和原因

**混合型文档处理**：一篇文档同时包含多种内容时，按内容类型拆分贡献到不同 Wiki。

### 问答阶段 Prompt：定义 Agent 如何使用 Wiki
- 回答前必须先获取证据文档
- Wiki 中提到前置条件/依赖 → 继续检索相关文档
- 文档没定义某能力 → **不能脑补**
- 定义什么时候搜索、什么时候直接读取、什么时候追依赖

## 10. 评估体系（让知识库可持续改进）

### 问答质量评估
- 测试用例：问题 + 分类 + 判断标准 + follow-up
- 真实调用完整链路，LLM Judge 按标准逐条判定
- 单题得分 = 通过标准比例

### 检索质量评估
- 分别执行关键词/向量路径，取并集
- 计算 recall / precision
- 分析哪些文档被命中、哪些被遗漏

### 对照开关
- source-only 模式：跳过 Wiki，仅检索原始文档 → 对比"编译前后"质量差异
- 关闭语义过滤：观察裸召回质量

**问题可拆开定位**：Wiki 生成质量？检索漏召回？语义过滤误杀？Prompt 不够明确？

---

## 11. 领域适配清单（跨场景复用）

把 LLM Wiki 应用到新领域时，回答以下问题：

```
□ Raw 层存什么？（原始素材的来源和格式）
□ Wiki 层的实体类型有哪些？（核心概念是什么）
□ 实体之间的关系怎么表达？（双向链接 + 自然语言描述）
□ 命名规范是什么？（slug 格式、前缀规则、哈希策略）
□ Ingest 的编译规则是什么？（Raw → Wiki 的转换逻辑）
□ Lint 检查哪些问题？（领域特有的一致性约束）
□ 需不需要拆分技能？（采集和分析是否足够复杂以分离）
```

## 12. 企业级 vs 个人级的关键差异

| 维度 | 个人知识库 | 企业产品知识库 |
|------|-----------|--------------|
| 检索入口 | index.md 导航足够 | **混合检索必需**（关键词+BM25+向量+RRF） |
| 查询者 | 知识库维护者本人 | 不同背景的大量用户 |
| 召回策略 | 模型阅读目录→选择 | 精确匹配+语义召回+排序融合 |
| 规模 | 数十到数百页 | 数百到数千页 |
| 质量门禁 | Lint 即可 | **AI 审核 + Lint + 评估体系** |
| Wiki 参与检索 | 不需要 | 需要独立索引机制 |
